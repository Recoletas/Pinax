# 体验页叙事运行时与阅读体验收口计划

状态：调研复核完成，待实施。日期：2026-08-14。归属：`G1.4 Experience Reading`、`G4.6 Narrative Context Runtime`。

本计划取代本文件早先的八个 RFC 排序。它不另建产品主线，也不先升级通用 Agent 框架；只处理当前真实试用中最影响体验的五个问题：新会话工具循环失败、模型步骤超时、世界书被忽略、正文拖沓且缺少故事推进，以及分段后桌面阅读面过空。

## 1. 用户问题与目标状态

### 1.1 已复现或由代码直接解释的问题

| 现象 | 直接原因 | 目标状态 |
|---|---|---|
| `叙事资料查询超过两轮限制` | `submit_narrative_beat_plan` 与世界/地理/历史查询共用 `toolRounds=2`；规划、查资料、修复任一步多走一轮就整轮失败 | 控制步骤与资料查询分别计数；资料预算用尽时带现有证据完成，不把整轮正文判死 |
| `叙事工具请求超时` | 实际是 provider 模型步骤的 20 秒硬超时，错误文案却写成工具超时 | 区分模型步骤、本地资料查询和整轮超时；按步骤配置预算并保留一次安全重试 |
| 新会话更容易失败 | `world_lookup`、`geo_lookup`、BeatPlan 默认同时暴露；开场资料稀少，却仍要求模型规划后自行决定多轮检索 | 开场先由应用确定性装配必要设定；模型通常只需一次规划、一次正文 |
| 世界书经常被忽视 | 项目已有成熟的 `matchWorldbookEntries()`，但生产叙事 Kernel 只放常驻规则、禁写、文风和主角色卡，未放当前场景命中的普通条目 | 当前地点、角色、历史绑定、关键词命中的世界书条目在请求模型前进入 Kernel；工具只补查未知细节 |
| 正文描写堆叠、拖沓、缺少故事感 | 标准 respond 硬目标为 900-1500 字符，补全逻辑又把低于下限视为可能未完成；BeatPlan 允许零因果步骤 | 以“回应、变化、后果、自然落点”判断完整，不以字符下限填满；计划至少包含可执行变化链 |
| 模型输出一大块 | 输出格式依赖模型主动空行；失败后只能靠 parser 兜底 | 模型自然段优先；仅对异常长且无空行的文本兜底重组 |
| 分段后电脑端显空 | 当前 parser 对未署名 narration 每个句号都拆块，每块又有 `0.58em` 间距；移动端窄行不明显，桌面被放大 | 恢复语义段落，一段通常 2-3 句；桌面只微调正文宽度、段距和左右工作区比例 |

### 1.2 本轮完成定义

完成后，一次普通体验回合应走以下稳定路径：

```text
玩家输入 / 新会话启动
  -> 应用装配连续性、当前角色与确定性命中的世界书
  -> 模型提交一个短 BeatPlan（控制步骤，不占资料轮次）
  -> 必要时并行执行一轮只读资料查询
  -> 模型依据已装配上下文和查询结果生成正文
  -> parser 生成语义段落，UI 按设备宽度呈现
  -> 回写本轮变化与来源，不回写纯气氛描写
```

普通回合预期为 2 次模型请求；确有资料缺口或计划修复时允许 3 次。保护上限只防死循环，不作为正常流程。

## 2. 调研复核结论

### 2.1 外部产品中值得采用的部分

1. [SillyTavern World Info](https://docs.sillytavern.app/usage/core-concepts/worldinfo/) 先按常驻、绑定、关键词和上下文预算装配资料，再生成回复。其文档也明确说明世界书只能引导模型，不能保证模型必然使用，因此 Pinax 应记录激活来源，但不应对所有“未体现”情况自动重写全文。
2. [NovelAI Lorebook](https://docs.novelai.net/en/text/lorebook/) 把最近正文、Memory、Author's Note 和 Lorebook 作为同一个上下文装配问题，并给条目独立预算。Pinax 应复用现有 Context Ledger，而不是把普通世界书依赖全部推给模型工具调用。
3. [NovelAI 编辑器设置](https://docs.novelai.net/en/text/usersettings/interface/) 把最大行宽作为阅读偏好，而不是把桌面正文无限拉满。Pinax 应解决段落节奏和工作区比例，不用全宽正文掩盖空白。
4. [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) 的 typed error、控制步骤和资料工具边界值得参考，但项目仍处于 developer preview，且以插件框架为中心。Pinax 当前不需要先迁移 SessionEventMap、Cordis 或 Goal domain。
5. [Pi Agent Harness](https://github.com/earendil-works/pi) 的价值在于缩短正常路径和减少抽象，而不是复制其代码或工具数量。对体验页而言，“确定性准备 -> 有界检索 -> 正文”比开放式多轮 Agent loop 更合适。

### 2.2 对旧 RFC 的裁决

| 旧提议 | 裁决 | 原因 |
|---|---|---|
| runtimeEvents v2 / SessionSurface | 延期 | 不能直接解决当前两类报错，改动面过大 |
| Continue / Auto steering 重构 | 删除 | `open/respond/extend/advance` 已实现，继续重做属于重复建设 |
| Goal domain | 延期 | 当前 SceneThread 足以承载软状态，先修语义和写回规则 |
| 合并两套 compaction 并加三事件锁 | 延期 | 与本轮 provider 超时、世界书缺席和阅读分段无直接关系 |
| append-style prompt | 保留原则，不做大重写 | 先删重复/冲突规则并用 ledger 测量，不能以任意 token 数字为目标 |
| 所有 marker / 世界书 / 文风违规自动重试 | 否决 | 会放大延迟、成本和重复正文；仅协议损坏允许本地修复，事实冲突按风险处理 |
| 新增世界书 keyword matcher | 删除 | `worldbookContextBuilder.js` 已有常驻、关键词、any/all、概率、绑定、starter 和预算逻辑 |
| 30+ 模板词、跨题材词库、文风指纹硬门禁 | 否决 | 词表脆弱、容易误杀；题材命名应由世界书定义，不应按“中西方”刻板规则判断 |

## 3. 目标架构：有界叙事流水线

不再把每一轮都当作开放式研究 Agent。保留现有 orchestrator 和 transcript contract，但将职责拆成四个有界阶段。

### 3.1 Prepare：应用侧确定性装配

输入：当前可见分支、玩家输入、SceneThread、运行时地点/角色/时间、世界书 revision。

输出：`NarrativeKernel`，新增 `activatedLore` block：

- 常驻 `rule/forbidden` 始终优先；
- 当前地点、角色、历史节点 `entryIds/sourceRefs` 的绑定条目其次；
- 最近 2-3 个可见回合与当前玩家输入触发的关键词条目再次；
- 新会话允许少量 starter：角色、地点、setting 各至多 1 项，不能把预设全塞入；
- 每项保留 `entryId`、`matchReason`、`matchedKeys`、`sourceRef` 和截断状态；
- 使用现有 token budget 与 Context Ledger，不新增向量库或第二套 matcher；
- 缓存键为 `worldbook revision + scene signature + visible tail revision`，世界书或场景变化时自然失效。

上下文优先级固定为：

```text
硬规则 / 禁写
> 当前玩家输入与玩家控制边界
> 当前地点、在场角色、历史绑定事实
> ContinuityFrame / SceneThread / 最近正文尾部
> activatedLore
> 场景摘要与较早记忆
> 可选工具结果
```

### 3.2 Plan：短控制步骤

BeatPlan 是控制面，不是资料工具：

- 不增加 `toolRounds`、`evidenceCalls`；
- schema 继续容忍 provider 的数组/字符串差异，但语义上必须有 `responseObligation`、`revealOrChange`、`endCondition`，并满足以下任一条件：一个非空 `causalStep`，或一个带 `action + result` 的角色动作；
- `functionalDetails` 最多 2 个，每个必须写明它改变了判断、动作或局势的哪一项；
- 计划只修复一次；修复仍失败时，使用由当前输入、SceneThread 和已有世界事实构成的最小保守计划，不重新走一轮开放式工具循环；
- `targetChars` 只作为软提示，不参与完整性判断。

### 3.3 Evidence：一轮正常查询，一轮条件恢复

资料工具只在以下情况调用：

- 用户明确询问设定、路线、历史、旧关系或记忆；
- BeatPlan 引用了 `activatedLore` 中没有的具体事实；
- 当前历史/因果状态标记冲突或 stale，不能直接采用。

预算分开记录：

| 预算 | 正常值 | 处理方式 |
|---|---:|---|
| 控制步骤 | 1，修复至多 1 | 不占资料轮次 |
| 资料查询轮 | 1，条件恢复至多 1 | 同轮调用并行执行 |
| 单轮资料调用 | 至多 4 | 超出返回 typed budget result |
| 全回合资料调用 | 至多 6 | 不抛弃已生成 transcript |
| 本地查询 | 800-1500ms | 超时作为 unavailable 结果交给正文阶段 |

达到资料上限时，orchestrator 不再抛出 `NARRATIVE_TOOL_ROUND_LIMIT`。它应追加 `NARRATIVE_EVIDENCE_BUDGET_EXHAUSTED` 结果，然后以 `toolChoice: none` 要求模型使用现有资料完成。如果用户明确要求核验而关键证据仍缺失，才返回“资料不足，未生成正文”的可恢复错误。

### 3.4 Write：一次正文，必要时一次续尾

- 正文请求不再暴露 BeatPlan 工具；只接收已确认计划和资料结果；
- 补全只在 provider 明确截断、引号/句子未闭合、BeatPlan 的 `endCondition` 明显未落地时触发；
- 删除“低于字符下限 70% 就补全”的条件，避免为凑字数追加景物和身体反应；
- 补全沿用同一计划和最后一句，不允许重新开场、再查资料或新增神秘事件；
- 无流式数据前的网络/超时错误可按同 transcript 重试一次；已经开始落字或执行工具后不自动重放，以免重复副作用和重复正文。

## 4. 叙事质量方案

### 4.1 从字符目标改为场景拍完整度

现有 `open 1200-1800 / respond 900-1500 / advance 800-1400 / extend 500-900` 会把“篇幅”误当成“完整”。调整为软区间，并取消硬下限补齐：

| 意图 | compact | standard | expanded | 说明 |
|---|---:|---:|---:|---|
| open | 500-800 | 750-1200 | 1000-1500 | 建立现场、角色行动与一个明确变化 |
| respond | 400-650 | 600-950 | 850-1250 | 完整回应玩家并产生一个后果 |
| advance | 400-650 | 600-950 | 850-1250 | 让已有因果向前一步，不代替玩家决定 |
| extend | 250-450 | 350-650 | 500-850 | 延长同一动作链，不建立新场景 |

这些数字用于输出预算和 UI 预期，不是验收门槛。短但完整的回复可以通过，长但没有变化的回复不应被认为更好。

### 4.2 四种场景模式，不做固定模板

BeatPlan 根据当前输入选择一种主模式，用于调整比例而非套格式：

- **对话**：2-4 次有效发言；动作只在改变潜台词、位置或关系时出现；不能用神态代替回答。
- **行动**：动作 -> 阻力 -> 可观察后果；环境只保留会影响动作的部分。
- **调查**：线索 -> 判断 -> 新问题或可执行方向；不得连续堆“异常、微妙、难以言喻”。
- **过渡**：地点/时间变化 -> 保留连续锚点 -> 到达后的第一个新事实；不写长篇旅途气氛。

### 4.3 精简行文契约

将现有多处重复的规则收敛为模型容易执行的五条：

1. 先回应玩家输入，再推进一个已有因果。
2. 每段只承担回应、动作、后果或过渡中的一个主要功能。
3. 每个场景拍最多一个环境细节和一个人物细节，除非它们直接改变判断或行动。
4. 不重复最近两轮已出现且没有新后果的动作、物件和情绪表达。
5. 变化落地后自然停下，不强加悬念、总结情绪或玩家选项。

模板句列表只保留极少量高置信短语作为观测指标，不作为自动重试门禁。重复检测优先比较最近两轮真实文本中的动作和名词，而不是扩张静态黑名单。

### 4.4 SceneThread 写回

- `currentObjective` 来源于尚未完成的场景目标，不能直接复制上轮 outcome；
- `recentOutcomes` 只记录可观察变化，不记录“气氛变得紧张”等描述；
- 同一地点不等于同一场景：目标完成、主要参与者切换或时间明显推进时建立新线程；
- 每轮只写回 1-3 个事实：落地变化、未决问题、角色即时目标；
- 手动编辑或删除正文后，按当前可见分支重建派生 SceneThread，不保留被删文字的摘要副本。

## 5. 世界书接入方案

### 5.1 不再依赖模型“想起来查”

在 `gameStore.generateAIResponse()` 建 Kernel 前构建一次 `worldbookContext`，或让 `buildNarrativeKernel()` 内部复用同一 matcher。必须避免两边各跑一遍产生不同命中集。

建议生产链：

```text
chatHistory + runtimeState + worldbook
  -> matchWorldbookEntries()
  -> buildWorldbookContext() / Context Ledger
  -> NarrativeKernel.activatedLore
  -> narrative orchestrator
```

`activatedLore` 不复制完整世界书，只放当前预算内条目。`world_lookup` 保留，用于模型确实需要的扩展信息。

### 5.2 新会话策略

新会话没有足够聊天关键词，不能因此得到空世界：

- 常驻规则、禁写、文风始终进入；
- 主角、当前对话角色和当前地点通过绑定进入；
- 从历史节点进入时，节点关联条目优先；
- 完全空白开场使用少量 starter，不按条目创建顺序把大量设定塞入；
- 若当前世界书没有结构化条目，只使用世界概述和写作基调，不虚构缺失角色。

### 5.3 遵循度与可诊断性

不新增一个常驻大面板。复用现有生成 trace / 调试信息记录：

- 激活条目数量与 entry IDs；
- 激活原因分布：constant / bound / history / keyword / starter；
- 被预算排除和被截断数量；
- 最终正文引用的工具 source refs；
- 世界书 revision 与 Kernel revision。

只有硬规则、禁写或唯一事实发生明确冲突时标记 `grounding warning`。普通条目没有在正文中出现不算错误，因为“进入上下文”不等于“本轮必须提及”。

## 6. 分段与阅读面方案

### 6.1 parser：语义段落优先

撤销“每个句号一个 block”的兜底，采用以下顺序：

1. 优先信任 marker 内模型给出的空行；一个自然段保留为一个 narration block。
2. 只有单块超过 260 个中文字符或超过 4 个完整句子且无空行时才兜底拆分。
3. 兜底以 2-3 句、约 90-180 字为目标；在角色切换、动作结果、时间/地点转换处优先断开。
4. 中文/英文成对引号内部不拆；短台词和紧随其后的归属动作尽量留在同一段。
5. 相邻不足 35 字的未署名 narration，如果没有场景或说话者切换且合并后不超 180 字，则合并。
6. `:::narration` 等协议残留继续本地清洗，不为 marker 问题重新请求模型。

这套规则只修复异常格式，不替模型重新写作。parser 测试使用边界样例，不做“所有文本都必须拆成固定段数”的过强断言。

### 6.2 桌面阅读密度

移动端当前观感基本可接受，主要改动限定在 `min-width: 1101px`：

- 正文阅读宽度保持约 55-65 个中文字符，不铺满整个中心区；
- 中心区与右侧资料栏的 gap 从当前视觉结果按截图微调，不能单纯扩大正文行长；
- 连续 narration 段距从 `0.58em` 收到约 `0.38-0.48em`；说话者切换和 user/assistant 回合仍保留较明显间距；
- `standard/compact/expanded` 只改变后续生成展开度的现状需要在文案上明确；阅读密度改由独立的字号、行宽和行距偏好负责；
- 禁止通过背景卡片、段落边框或大色块填空，保持现有蓝白档案与小说阅读面。

UI 阶段必须先截取 1440、1280、390 三个宽度的同一长对话，再改 CSS；验收关注正文行宽、段落节奏、输入区可见和右栏层级，不要求截图像素完全一致。

## 7. 错误、超时与恢复

### 7.1 错误名称必须指向真实阶段

| code | 用户文案 | 是否自动重试 |
|---|---|---|
| `NARRATIVE_PROVIDER_TIMEOUT` | 叙事模型响应超时 | 未开始输出时至多 1 次 |
| `NARRATIVE_LOCAL_LOOKUP_TIMEOUT` | 本地资料查询超时，已使用现有资料继续 | 不重试整轮 |
| `NARRATIVE_AGENT_TIMEOUT` | 本轮生成超过总时限 | 不自动重放已执行步骤 |
| `NARRATIVE_EVIDENCE_BUDGET_EXHAUSTED` | 已达到资料查询上限，将使用现有资料完成 | 不是致命错误 |
| `NARRATIVE_GROUNDING_REQUIRED` | 缺少本轮明确要求核验的资料 | 用户可重试或调整资料 |

### 7.2 超时按步骤分配

不要只把所有步骤统一从 20 秒继续加大。初始建议值：

- BeatPlan / 路由步骤：35 秒；输出短，重点是兼容慢渠道首包；
- 正文步骤：60 秒；如果 adapter 能观察流式活动，改用 20 秒无活动超时而不是总墙钟；
- 单次补全：45 秒；
- 整轮：100 秒保护上限；
- 本地资料工具：800ms 起，允许按索引规模放宽到 1500ms，但失败不终止正文。

以上均放入单一 runtime config，trace 记录每一步的 `startedAt/duration/outcome`。后续根据 MiniMax、OpenAI-compatible、Anthropic-compatible 的真实样本调整，不能把测试机数字写成永远不变的协议。

## 8. 实施阶段

### P0：冻结问题与可观察性（0.5-1 天）

涉及：`narrativeAgentOrchestrator.js`、provider adapter、production observer、少量测试夹具。

- 固定 3 个最小样本：空白新会话、带世界书角色/地点的开场、连续 3 轮对话；
- trace 分开记录 plan、evidence、write、completion 的耗时和计数；
- 保留当前两种错误作为回归样本；
- 记录 parser 生成块数、平均块长、最长块长；
- 不新增复杂 dashboard，现有 trace JSON 足够。

Gate：能从一次失败记录中判断是 provider、资料工具、预算还是 parser 问题。smoke 只验证链路能走完和错误可定位，不承担文风质量判定。

### P1：运行时止血（1-2 天）

- BeatPlan 从资料轮次计数中剥离；
- 资料预算耗尽改为 typed result + 强制完成，不再直接抛错；
- provider timeout 文案纠正，按 plan/write 分配超时；
- 安全重试只发生在正文和工具均未落地之前；
- 默认工具目录不再无条件暴露 geo；根据地点存在、用户意图和 Kernel 缺口决定。

Gate：三个最小样本各执行 3 次，不再出现“两轮限制”；慢渠道超时时能正确指出阶段；不要求九次正文都达到人工优秀。

### P2：世界书确定性接入（1-2 天）

- 把现有 matcher 接入 `NarrativeKernel.activatedLore`；
- 完成新会话 starter、地点/角色/历史绑定和预算优先级；
- ledger/trace 记录命中和排除原因；
- 删除旧 RFC 中的第二套 matcher、跨题材词库和全局违规重试设计。

Gate：使用 3 个有明确唯一事实的世界书样本，Kernel 必须命中正确条目且不全量注入；正文不要求逐字复述，但不得与硬规则和唯一事实冲突。

### P3：BeatPlan 与行文收口（2 天）

- BeatPlan 恢复最小因果语义，保持 schema 兼容；
- 输出长度改为软区间，删除按字符下限补全；
- 落实四种场景模式和五条行文契约；
- SceneThread 只写回可观察变化、未决问题和即时目标；
- 同一计划的补全不得再次起势。

Gate：3 类场景各连续生成 3 轮，由人工按“是否回应、是否变化、是否重复、是否堆描写、是否自然承接”五项记录。每项用通过/轻微问题/失败三级，不构造一个虚假的综合分数；阻断项只有不回应、事实冲突、严重断裂和连续重复。

### P4：语义分段与桌面阅读（1-2 天）

- parser 从逐句拆分改为异常长段兜底；
- 补 marker、引号、短段合并和流式边界测试；
- 桌面调中心区、正文 measure 和 narration 段距；移动端保持现状为主；
- 旧消息检测到 leaked marker 时继续重解析，正常旧消息不做批量迁移。

Gate：同一回复在 1440、1280、390 下无协议头泄漏、无横向溢出、输入区可用；桌面长文不出现句句一段，移动端不因合并退回整屏大段。

### P5：真实渠道验收与清理（1 天）

- MiniMax、OpenAI-compatible、Anthropic-compatible 各跑：新会话 1 次、带世界书连续 3 轮 1 次；没有密钥的渠道记录为未测，不用 mock 冒充；
- 删除本轮确认无调用的旧限制分支和过时注释；
- 更新三份旧体验计划为“已由本计划收口/剩余历史参考”，避免重复执行；
- 更新 `docs/STATUS.md`、`docs/PLAN.md` 和测试基线。

Gate：构建与相关 contract 测试通过；真实渠道结果有 trace 和简短人工结论。真实 smoke 不要求“每次都是优秀文学作品”，只要求无硬失败、世界事实可用、连续三轮可读。

## 9. 测试范围

本轮不追求增加大量测试，只补关键边界：

- orchestrator：控制/资料计数分离、预算耗尽仍完成、provider timeout 分类、安全重试；
- worldbook：新会话 starter、绑定优先、关键词命中、预算截断、revision 缓存失效；
- BeatPlan：宽松输入归一化后仍须有最小变化链；
- presentation：正常自然段不拆、异常长段分组、引号内不拆、marker 不泄漏、相邻短叙述合并；
- SceneThread：outcome 不变 objective、删除/编辑后按可见分支重建；
- 浏览器 smoke：桌面和移动端各一条长回复，操作与溢出检查。

优先合并现有重复夹具；预计新增或改写约 15-25 个定向用例，不把总测试数量、覆盖率或视觉像素一致性设为本轮质量目标。

## 10. 非目标与风险控制

本轮明确不做：

- runtimeEvents v2、SessionSurface、Goal domain 或 Cordis；
- 向量检索、embedding 服务或全新世界书 schema；
- 全文风格指纹硬判、30+ 禁句和中西题材词库；
- 为普通风格偏差自动重写整段正文；
- 体验页整体视觉改版、主题1适配或新的设置面板；
- 将 smoke 提升为文学质量自动评测。

主要风险与控制：

- **世界书上下文变长**：沿用 token budget，绑定/常驻优先，trace 显示截断。
- **取消字符下限后回复重新变短**：由 BeatPlan 的完整变化和人工 3x3 复读约束，不恢复硬补字数。
- **放宽超时导致等待过长**：区分步骤与活动超时，保留取消；不无限重试。
- **合并段落后移动端变成大块**：异常长段上限仍存在，并用 390px 真实文本验收。
- **模型仍忽略普通 lore**：只把硬冲突设为阻断；普通 lore 通过激活 trace 和人工样本观察，不引入循环重写。

## 11. 最终交付物

1. 有界且可诊断的叙事运行时，不再以“两轮限制”终止普通新会话。
2. 生产叙事链路真实接入现有世界书 matcher 和 Context Ledger。
3. 以因果变化而非硬字符下限驱动的 BeatPlan、正文与 SceneThread。
4. 正常自然段优先、异常长块兜底的 presentation parser。
5. 桌面更紧凑、移动端不退化的主题2阅读面。
6. 少量定向测试、真实渠道 trace 和 3x3 人工复读记录。
