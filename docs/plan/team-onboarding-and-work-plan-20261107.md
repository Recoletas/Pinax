# Pinax / Pinix 新成员入门与分工安排

更新：2026-11-07。面向第一次接触项目、准备参与开发的成员。

本文解释项目是什么、代码放在哪里、如何开始，以及第一轮建议怎么分工。当前分工是建议安排，A/B/C 尚未绑定具体成员；时间是估算，不是已承诺的发布日期。已有能力以代码和验证记录为准，下面的计划不代表功能已经完成。

## 1. 我们在做什么

Pinax 是面向创作者的 AI 辅助创作工作台。作者可以组织作品和章节、编写正文、管理人物与世界设定、导入参考资料，并让助手查阅资料、讨论或修改内容。漫画、插画、视频和跑团是已有的其他创作方向。

参与开发不是从零搭建这些功能。现有 Web 产品已经有工作区、编辑器、助手、设定与资料等实现；近期主要把可共享的业务代码抽进独立 Core，让不同端维护各自的界面和平台适配，共用同一套业务规则。

主要技术是 Vue 3、Vite、Pinia，正文编辑基于 Tiptap/ProseMirror；服务端使用 Express，移动端通过 Capacitor 对接 Android。新人先能读懂 Vue 组件、JavaScript 模块、异步函数和 Git 分支即可开始，不必第一天就熟悉 Agent 或 Android 全套机制。

Pinix 是独立的移动端产品仓库，基于 Pinax 的代码发展，以 Android 为先，也能在浏览器中开发和预览。它不是给公网网站换一个手机尺寸，也不是一套重新实现的小说数据模型。输入法、触控、键盘遮挡、前后台切换、文件和设备保存等问题，需要在移动端专门处理。

当前第一轮团队工作的重点是：在已有基础上，交付可靠的移动写作、保存恢复和媒体创作闭环。不是同时重写所有页面，也不是把每个已有功能都一次性搬到手机上。

## 2. 仓库地址与区别

| 仓库 | 地址 | 负责什么 | 日常开发位置 |
|---|---|---|---|
| Pinax | https://github.com/Recoletas/Pinax | Web 产品、Web 平台适配、Express 服务、工程与产品文档 | Web 页面和 Web 服务改动在这里 |
| Pinix | https://github.com/Recoletas/pinix | 移动产品、移动交互、Capacitor Android 与设备适配 | 移动端任务主要在这里 |
| pinax-core | https://github.com/Recoletas/pinax-core | 平台无关的共享业务模型、规则与执行流程，包名 `@pinax/core` | 需要两端共用的业务修改在这里 |

私有仓库需要维护者先授予访问权限。仓库名称有历史差异：Pinax 代码中仍能看到 `text-game-framework`、WriterHelper 等名称；它们不是需要另外克隆的产品。

Pinax 主仓还保留桌面/Electron 相关代码；Pinix 使用自己的 Capacitor 宿主，不需要复制桌面壳或安装 Electron 才能开发移动端。

另外有 Next 方向，目标更精简。本轮不安排 Next 改造，也不要求它启用 Core 中的全部能力。不要为了移动端任务去修改 Next。

## 3. 架构：各层分别负责什么

```text
Pinax Web 界面                         Pinix 移动界面
Vue 页面、组件、交互                    Vue 页面、组件、触控交互
          │                                      │
          └──────── @pinax/core ──────────────────┘
                    模型、业务规则、用例
                    上下文、Agent、修改与恢复流程
                          │
                    由各端注入平台能力
                  ┌───────┴─────────┐
           Web / Node 适配       Android / WebView 适配
           存储、文件、网络       存储镜像、文件、生命周期
```

这里的“注入”指：Core 决定怎么处理业务，调用端提供“读取章节”“保存数据”“发送模型请求”等实际能力。Core 不直接拥有浏览器、Android 或服务器的运行环境。

### Core 目前的范围

Core 0.16 包括作品/章节、设定条目、大纲、速记和素材的业务模型与服务；修改提案、权限、采用/拒绝/撤销、事务与恢复；上下文组装、写作编排、Agent 会话及工具执行；以及媒体和跑团的共享业务模块。

这是一套按模块引用的共享业务包，不是要求每个端开启所有功能。页面、样式、Vue 组件、Capacitor 插件、实际数据库连接、磁盘写入、模型 HTTP 请求和 SDK 装配留在各端。兼容现有接口的 Core 修复，各端更新依赖后可以复用；新增端口或破坏接口的修改，仍需要调用端适配。

### 按什么标准决定改哪个仓库

| 例子 | 应改的位置 |
|---|---|
| 同一段修改重复采用、章节修订判断错误，两端都应遵循同一规则 | Core；宿主补必要接线 |
| 手机软键盘遮住输入、触控菜单不好用、侧栏布局不合适 | Pinix 界面 |
| Android 保存失败、前后台恢复、文件分享 | Pinix 平台层；共用业务规则仍调用 Core |
| Web 的服务器代理、部署配置或浏览器专属行为 | Pinax Host |
| 漫画生成结果应该怎样归属某一页、怎样处理旧请求结果 | 优先检查 Core 既有媒体逻辑；平台请求与页面展示分端适配 |

不要在 Pinix 再写一份章节模型、世界书状态或 Agent 循环，也不要把 UI 和 Android API 放入 Core 来追求“所有代码都共享”。

### 保存与 AI 修改的基本关系

界面编辑 → 调用业务服务 → 唯一数据所有者执行写入 → 平台确认保存 → 界面显示成功。

AI 生成的候选与正式作品是两种状态。审阅模式需要作者采用；自动修改也要走正式写入、修订与恢复链路。不能只把文本显示出来就标记为已经写入，不能在保存失败后清除唯一候选。

当前 Web 仍有浏览器正式数据；本地文件/SQLite 相关能力不代表所有 UI 已切换存储。Pinix 已有浏览器工作集与 Android 双槽快照镜像，部分保存/采用链路等待持久化确认；这也不代表全部 owner 都已经完成设备验收。不要一开始就全量替换存储。

## 4. 先认识这些目录

| 位置 | 需要知道的内容 |
|---|---|
| `src/pages/`、`src/components/` | 页面与组件；写作入口主要在 Authoring 及其子组件 |
| `src/composables/` | 页面交互与流程装配；常见入口为 `useAuthoring*` |
| `src/services/`、`src/stores/` | 平台装配、服务和状态；很多旧路径现在转发 Core，不一定是业务实现本体 |
| Pinix 的 `src/platform/` | 原生存储、文件、网络和生命周期适配 |
| Pinix 的 `android/` | Android 工程，使用 Capacitor 和 Gradle Wrapper |
| `server/` | Express 与服务端能力，不是直接打进手机的 Node 后端 |
| `vendor/core/` | 固定版本包和来源记录，不是日常编辑源码的位置 |
| 独立 Core 的 `src/` | 共享业务源码；按 domain、usecases、agent、context 等模块组织 |
| `docs/STATUS.md` | 当前任务与事实，开始工作先看；历史记录不等于当前待办 |
| `AGENTS.md`、`agent-skills/` | 仓库协作与验证约定；使用 AI 开发工具时也应遵守 |

首次不要通读整个 Authoring.vue 或全部历史计划。先从一个操作追踪到负责它的服务和 Core 模块，建立局部认识。

## 5. 建议的上手顺序

### 第一步：取得正确代码并跑 Web 预览（半天至一天）

先准备 Git、Node 22.22.3 和 npm 10+，以仓库 `.nvmrc` 与 package.json 为准。首次只做浏览器预览，不必马上安装 Android 工具或申请模型额度。

```sh
git clone -c core.symlinks=true https://github.com/Recoletas/pinix.git
cd pinix
git switch --track origin/refactor/core-host-migration
git switch -c feat/your-first-task
npm ci
npm run doctor
npm run dev
```

将任务分支名换为实际任务。若集成分支已经合入 main，维护者应通知成员从最新 main 建分支，不再机械执行旧分支命令。

浏览器打开终端输出的地址，通常是 `http://localhost:5173`。Windows 若受 npm.ps1 执行策略影响可用 npm.cmd。项目有符号链接，Git for Windows 需要相应支持；Windows 和 WSL 使用各自的 checkout、node_modules 和工具链，不混用安装结果。详细步骤见 Pinix [组员上手指南](https://github.com/Recoletas/pinix/blob/refactor/core-host-migration/docs/getting-started.md)。

前端预览不需要配置全部 AI 服务。实际模型功能涉及 Express（通常 3001）和助手运行器（通常 8451），配置与启动由维护者协助，见[运行包部署说明](../engineering/agent-runtime-deployment.md)。手机上的 localhost 指手机自身，不是开发电脑；使用既有网络适配，不在组件里写死电脑地址或密钥。

### 第二步：以用户身份走一遍（半天）

用合成内容创建作品、输入中文、新建章节、切章、刷新恢复，再试设定条目、资料导入和备份导出。拿到测试模型配置后，再试助手生成、采用与撤销；媒体方向补一遍漫画生成和重开。

记下卡住的操作、复现步骤和预期，不要先改布局。首次目标是能解释“用户点了什么，内容保存在哪一层”，而不是把页面都点开一次。

### 第三步：读最少的文档并追一条调用链（一天）

按顺序读本仓库 AGENTS、STATUS、[当前架构](../engineering/current-architecture.md)，再读负责方向的代码。移动端补读 Pinix 的 architecture、reuse-ledger 和 verification-and-release。

推荐从“保存当前章节”开始：定位页面动作、chapterCoreStore、Core 章节 service，再找到平台保存与回执。把调用关系、实际写入位置及失败时保留什么写成一小段任务说明。不要另写一份庞大的架构报告。

### 第四步：完成一个小而完整的任务（两至三天）

先接范围清楚的问题，例如一个移动编辑交互、一处保存回执呈现、一个生成失败后可重试的问题。包含操作入口、正常结果、失败处理和必要验证；让维护者 review 后再扩大范围。

如需修改共享规则，再克隆独立 Core，而不是所有人第一天都同时改 Core：

```sh
git clone https://github.com/Recoletas/pinax-core.git
cd pinax-core
npm ci
npm test
```

已有读取、写入和编辑能力优先复用。遇到不确定的数据归属，先带具体调用路径和问题与维护者对齐。

## 6. 建议分工：三个方向和一个集成负责人

建议三位成员分别负责 A/B/C，维护者负责 Core 合同与跨仓集成。可以按经验交换方向，不把字母当作永久人员绑定。每个方向先交付一个可验收流程，随后继续承担该方向的长期建设。

### A：保存、恢复与文件能力

目标是让作者确定“写进去的内容不会因为切页、退出或失败而消失”。

- **首批任务**：盘点正文、设定、资料和候选采用的实际保存入口，优先补齐第一轮要用到的持久化确认；串通备份导入/导出与重启恢复。先复用现有快照与 Core 事务，不同时引入一套新存储。
- **主要位置**：Pinix `src/platform/storage/`、`files/`、`lifecycle/` 及保存适配；共享规则需修改时到 Core 的 Store、事务和恢复模块。
- **首批验收**：创建作品→写两章→编辑设定→切前后台→退出重开，内容一致；模拟一次保存失败，输入或候选仍可恢复，重试不重复插入；备份恢复后能重新打开。
- **与其他组的接口**：向 B 提供明确保存/失败状态和重试方式；向 C 提供媒体文件保存及引用恢复能力。先写清目前支持哪些数据，避免承诺“所有东西都可靠保存”。
- **后续方向**：完整文件能力、备份迁移、设备恢复与性能；是否切换默认存储单独决定。

### B：移动写作与助手使用体验

目标是让作者在手机上完成持续写作和改稿，而不是只能展示桌面界面。

- **首批任务**：正文编辑、章节切换与目录；中文输入法、软键盘遮挡、选区和撤销；助手候选在原位置审阅、采用/拒绝及返回正文。
- **主要位置**：Pinix 写作组件、Authoring 子组件和 composable；审阅与修订规则复用 Core。
- **首批验收**：中文连续输入、粘贴与撤销正常；切章返回保留工作位置；助手生成→采用→刷新后还在→撤销，结果可解释；运行中改变下次参数不丢当前任务。
- **与其他组的接口**：消费 A 的保存回执，不自己写另一套存储；需要共享 Agent 行为时交由维护者协调 Core。视觉改动先做一个小范围并截图确认，避免整页重写。
- **后续方向**：设定/资料移动编辑、长文档性能、助手交互与无障碍。

### C：漫画与媒体创作闭环

目标是先让一个媒体流程真正可用，不以“接通生成接口”作为完成。

- **首批任务**：以漫画的一页为样例，正文选段→生成分镜→生成图片→选择结果→保存→重开。请求失败、取消、结果未知和已有候选都要能理解和继续操作。
- **主要位置**：Pinix 媒体工作台和平台请求适配；页/分镜/请求归属与生成编排复用 Core media 模块。
- **首批验收**：至少两格可连续生成且归属正确，第一格结果不会覆盖下一格；候选不会把后续生成永久锁住；失败不丢分镜，重开能看到已保存结果；有一次真实渠道验证。
- **与其他组的接口**：使用 A 的媒体保存/引用能力。A 尚未完成时可以验证独立组件或使用标明范围的临时夹具，不能以夹具通过冒充文件保存完成。
- **后续方向**：多格一致性、漫画导出、插画、视频任务及素材复用。视频可在漫画闭环稳定后接续，不要求首轮同时完成。

### 维护者：共享 Core 与集成

负责 Core API 与版本、任务优先级、共享文件冲突、跨仓更新、评审和集成。先确定共用的保存回执、资源引用与任务目标，再让成员并行，不要求成员自己争夺接口所有权。

每位成员负责自己的实现与自查；维护者承担跨方向复验。模型服务配置、测试额度和必要设备也应在相关任务开始前提供。暂时没有权限或设备的任务调整范围，不用假结果填补。

## 7. 大致时间安排

以 **3 位成员、每人每周约 10–15 小时，另有维护者参与评审与集成** 为估算，首个可验收的组合版本建议安排 **6 周左右，预留至第 8 周**。这是移动写作、保存恢复和一条媒体闭环的时间，不是全部产品方向做完的时间。

| 时间 | 共同目标 | A | B | C |
|---|---|---|---|---|
| 第 1 周 | 环境跑通、体验现状、完成首个小任务 | 追踪保存/恢复链路并复现一个问题 | 复现输入/导航/审阅问题并完成小修 | 跑通现有漫画流程，确认渠道与失败点 |
| 第 2 周 | 确定第一批接口和验收样例 | 定义并实现所选数据的保存确认与失败回执 | 完成一个移动编辑切片并确认视觉方向 | 补齐选段到分镜，明确图片结果与资产引用 |
| 第 3–4 周 | 三个方向各交一条完整流程 | 重开恢复、失败重试与备份样例 | 输入/切章/助手审阅闭环 | 连续生成、候选选择、保存与失败恢复 |
| 第 5 周 | 合并后实际联调 | 与 B/C 核对保存及迟到结果 | 在真实设备走连续写作与改稿 | 真实渠道与重开验证，修复跨组问题 |
| 第 6 周 | 形成候选版本 | 恢复与备份复验 | 移动体验与回归 | 媒体流程与回归 |
| 第 7–8 周 | 必要时使用的缓冲 | 设备、迁移和异常问题 | 长文档、输入法与设备差异 | 渠道稳定性和媒体文件差异 |

如果成员尚不熟悉 Git、Vue 或异步代码，先加一周基础熟悉；如果是全职开发，可在第一周实测后缩短安排，不直接按工时比例保证交付日期。每周根据实际结果调整，不为了追日期跳过恢复与设备验证。

建议每周一次约半小时的演示与任务调整；中途只报告已完成、卡点和需要别人提供的接口。演示走真实操作，不只展示代码或页面截图。

## 8. 修改 Core 与同步到另一端

Core 的源码只在独立仓库中改。在任一宿主中临时连接它开发：

```sh
npm run core:dev -- /path/to/pinax-core
npm run core:status
```

重启相关开发服务后调试。完成后 `npm run core:restore` 恢复固定包。Core 测试、版本和提交在 Core 仓库完成；维护者确认新版本后，各端执行：

```sh
npm run core:update -- /path/to/pinax-core
```

该命令更新固定包、来源记录和依赖锁文件。各端仍需验证和重新构建；已经装好的 APK、运行器和公网服务不会因此自动更新。具体步骤见 [Core 开发与更新](../engineering/core-development.md)。

同一版本由维护者统一交付，不让三个人各自用不同内容覆盖 0.16.0。成员可以提交 Core 修复分支，但版本发布和宿主升级集中协调。需要修改双方接口时，在任务中列出 Core 和宿主各自的改动与兼容方式。

## 9. 如何提交、验证和交接

每个任务写清用户问题、改动范围和通过标准，从确认过的集成基线建分支。提交应是一项可 review 的完整改动，不要求每改几行就提交，也不把多项无关功能攒成一个大补丁。使用仓库规定的 Conventional Commit 格式，保留真实作者身份。

开发阶段做相关检查，交付前按仓库要求验证：Pinix 目前要求 `npm run verify:full`；涉及移动平台补 `npm run mobile:check` 及相关移动构建/同步。纯文档和 Web 小改按各自仓库的当前规范选择必要检查。不要通过删除测试或扩大预算掩盖失败。

写入类任务至少核对正常保存、一次失败、重试和重开；UI 任务提供实际截图并看过深浅主题与目标尺寸；AI/媒体任务分别说明模拟接口与真实模型结果。没有 APK/真机、没有真实渠道时明确写未验证，Web 构建成功不等于设备通过。

提 review 时交付以下内容即可：

1. 解决了哪个操作问题，怎样进入和复现。
2. 主要改了哪些位置，是否涉及 Core 或存储格式。
3. 实跑验证、退出结果及必要截图。
4. 未验证范围、仍存在的问题和下一步。

维护者合并后同步其他端需要的 Core 版本。不要把整个 Web 仓库覆盖到 Pinix 来同步功能；平台差异保留在适配层，按任务迁入需要的改动。

## 10. 开工前确认与完成定义

维护者在派工前确认 A/B/C 具体成员、每周投入、当前分支和首个任务；为成员开通仓库权限，给涉及模型的成员提供测试方式，为设备验收确定至少一台 Android 设备。没有必要等所有后续方向设计完成再开始。

第一轮完成的标准是：新成员能独立拉取和启动；作者能写作、使用助手修改、保存并重开；一条漫画流程可以从正文走到可恢复的产物；组合版本有实际设备和真实渠道的证据。未完成的方向仍留在各组后续清单，不以页面已经存在代替验收。

后续长期范围仍包括资料/设定的完整移动体验、媒体扩展、文件与设备能力、性能和发布。它们属于持续开发，不再全部混称为“抽 Core 的前置工作”。
