# 助手正文修改、权限与推演现场整合计划

日期：2026-10-09。状态：**已本地实施，组合验收通过；未提交部署。** 实际行为和验证边界见[实施记录](../agent-runs/assistant-editing-20261009.md)。

基线：`main@44466ab1b63b4dfde6c40f98997fad00a6c5de29`，另有本地助手 Markdown、过程区间距和推演暗色底色修复。执行时保留这些修改。本计划接续 [PR #6 整合](./pr6-agent-integration-20261009.md)，补全使用流程和执行约束。

## 1. 本轮要达到的效果

作者说“按第一个方向续写”，助手能够接着前面的讨论，查阅必要资料，把续写建议放到正文对应位置。作者可以逐处接受、拒绝，或者明确授权后让助手直接修改。助手消息负责说明做了什么、引用了什么，不再把聊天里输出长文当作已经修改正文。

同时整理三处界面：

- 输入区原来的“讨论故事／写作与修改／查阅资料”改为清楚的权限控制，修正浮层与触发按钮错位。
- 右侧工具轨分成 AI 操作、作品内容、辅助视图三组，沿用现有结构和图标体系。
- “现场”并入“推演”，当前场、人物入场确认和生成放在同一流程里；现场数据继续供其他功能使用。

### 保留的边界

- 保留 pi + Storyflow + Pinax 的现有分工，不另建 Agent 内核。
- 正文左栏、章节目录、完整设定页结构不改；不再加一套工作区导航或卡片首页。
- 正文修改在中央稿面审阅；设定、大纲修改在各自现有面板审阅；检索结果留在助手。
- 助手自动化、推演半自动化、批注轻量修改各有入口，共用必要的权限、事务和冲突保护，不强行改成同一种聊天操作。
- 未采用内容不能进入保存的正文、现场识别或正式记忆。默认仍需作者确认。
- 本轮计划不包含上线、重启服务或替换用户正在运行的实例。

### 已查明的“只发在助手里”问题

一次连续对话先讨论情节，再要求尝试其中一个方向。后续任务实际调用了两次 `world_lookup`，没有调用 `submit_edit_proposals`，最后输出长篇正文并被判为完成。

该任务**具备修改工具，提示中也已有交付提议的要求**。运行时通用提示仍要求写作请求“产出叙事正文”，与 Pinax 的提议要求冲突；完成判定又接受非空文本。问题涉及任务协议和完成判定，不能仅靠给按钮改名解决。

核对位置：

- `src/services/agents/storyagent/agentEngine.js`
- `src/services/agents/storyagent/authoringIntegration.js`
- `src/services/agents/storyagent/authoringAgentTurn.js`
- `runtime-extensions/assistantProposalTool.js`
- 运行包 `.runtime/storyagent/dist/pinax/prompt.js` 的初始与继续任务提示

运行包是构建产物，最终修复必须进入固定版本上游源码或仓库内受控扩展，不能只手改 `.runtime`。

## 3. 作者实际怎么使用

### 3.1 讨论与查阅

默认权限为“审阅修改”，但普通讨论不产生修改。问“这个人物为何离开”，助手读取允许的资料并回答；问“有哪些写法”，给出方向。权限表示允许做什么，不等于每轮必须改稿。

选择“只读”后仍能讨论、检索和给建议。若作者要求落到正文，提示切换至“审阅修改”，保留原请求；不伪称已经完成修改。

### 3.2 写作与修改

1. 作者在当前章节提出续写或改写要求，也可以承接上轮“试试第二条”。
2. 助手结合对话解析任务和落笔位置，读取当前有效正文及必要设定。
3. 生成结构化提议；中央稿面对应位置出现待审阅内容。
4. 助手简短说明修改位置和主要变化，提供“查看修改”。
5. 作者逐处接受、拒绝，或对一组相关修改整组处理。
6. 成功写入后更新字数、保存状态、版本记录和现场失效标记。

“续写”默认接当前章节结尾；“改这段”使用发起时冻结的选区。没有明确目标且无法从上下文唯一确定时，先澄清。不能将未知目标回退成任意章节或把聊天全文直接写入。

### 3.3 自动修改

作者显式选择“自动修改”，默认只授权当前章节。助手交付的合法提议通过相同校验与事务直接应用，保留修改摘要、“查看修改”和“撤销本次”。设定、大纲和其他章节需要额外范围授权。

自动模式仍不能绕过冲突、保存失败、对象删除或授权撤销。遇到这些情况保留提议，转为等待处理。现场人物入场仍需作者确认，本轮不把自动改稿等同于自动确认故事事实。

## 4. 界面安排

### 4.1 助手输入区

保留现有输入区布局。底部权限按钮显示“只读”“审阅修改”或“自动修改”，旁边用简短文字显示写入范围，例如“当前章节”。范围详情进入同一浮层的次级区，不在输入框上方堆提示。

菜单内容：

| 选项 | 简短说明 |
| --- | --- |
| 只读 | 查阅资料、讨论内容 |
| 审阅修改 | 修改先交给你确认 |
| 自动修改 | 在授权范围内直接修改 |

“检查文稿”“生成插图”回到现有工具入口；若保留输入区快捷方式，放入加号菜单的操作分组。加号仍首先承担添加文件、引用章节，不能把这些功能藏掉。“参考与技法”继续是参考选择，不代表写入授权。

完整助手与右栏助手共享同一会话权限和任务状态，切换视图不能重置请求或产生第二份修改。

### 4.2 浮层定位

当前侧栏和完整助手使用不同定位参照，需统一为触发按钮的实际边界：

- 浮层对齐按钮边缘，按可用空间向上或向下展开，贴近触发点。
- 坐标换算覆盖页面缩放、滚动容器、移动端软键盘；不混用不同 offsetParent 的坐标。
- 到屏幕边缘时收束宽度和位置，不遮住发送按钮，不被右栏裁切。
- 滚动、窗口变化时重算；Escape 关闭并还原焦点，键盘可选择。
- 加号菜单沿用已确认的向下展开行为，不能借修权限菜单再次改回遮挡输入框。

### 4.3 中央稿面修改审阅

正文差异紧贴实际段落。新增文字出现在插入处；替换显示旧文和新文的关系，长段落可折叠旧文；删除有明确标记。沿用正文宽度、字体和行高，避免把稿面变成多个大框。

每处提供“接受／拒绝”，一组修改提供“全部接受／全部拒绝”和前后定位。颜色之外同时有文字或图标区别，深色模式不能出现明显灰色带。

候选稿期间允许作者继续编辑正文。冲突显示在相关修改处，其他可独立应用的修改仍可审阅。首轮不增加第二套富文本候选编辑器；需要调整候选时，可继续要求助手修改尚未采用的提议。

右栏助手保留简短修改列表和处理进度；正文是主要审阅位置。大纲和设定提议打开各自现有面板，在相应条目展示差异，工具轨用小点提示待处理内容。

### 4.4 右侧工具轨

按现有图标顺序整理间距：

| 分组 | 工具 |
| --- | --- |
| AI 操作 | 助手、推演、批注 |
| 作品内容 | 大纲、角色、设定 |
| 辅助视图 | 记忆、双栏 |

分组通过轻微间距或细分隔体现，不增加占宽的大标题。保留选中、悬浮说明和待处理标记。协作等条件入口继续按现有条件显示，不在整理时删除。

### 4.5 现场并入推演

推演面板顶部显示紧凑的“当前场”摘要：地点、时间、在场人物。点击展开后可修改、查看候选和确认入场。其下继续是推演条件和生成操作；草稿仍在中央正文落笔处预览。

展开区承接原现场的详细事实、来源、未解决事件和场景／因果信息，次要信息放入“详情”，不丢掉原有能力。左栏底部的“当前场”入口改为打开推演并展开此区。

完成等价接线后才移除工具轨的独立“现场”入口。现场数据不是推演组件的私有状态，助手、角色和其他消费者仍能读取共享快照。

## 5. 任务与完成协议

### 5.1 区分意图与权限

内部任务意图建议为 `answer | edit | mixed`；权限为 `read | review | auto`。二者分开传递。意图结合本轮请求、前文和选区判断，不能只匹配“写”“改”等关键词。信息不足时返回需要澄清，不自动扩大范围。

初始任务和 resume 使用同一份助手任务约定，移除助手路径上“写作必须直接产出正文”的冲突提示。推演本身的叙事输出约定保留在推演任务内。

### 5.2 完成条件

| 任务 | 合格的交付 |
| --- | --- |
| 讨论、检索 | 有效回答；引用只能来自实际读取结果 |
| 写作、修改 | 有效且目标明确的提议；或明确的澄清／受阻结果 |
| 混合任务 | 回答及要求的提议均存在 |

模型说“写好了”不能改变任务状态。修改任务缺少提议时，在原预算内允许一次纠正；仍失败则提示未形成可应用修改并保留已有文本，不标记为“已修改”。不得用前端正则从聊天答案自动抽取正文落库。

工具预算临近耗尽时，要为交付提议保留机会，不能统一禁用所有工具再强迫输出正文。修正提示、工具可用性和最终验证必须同步。

任务状态与提议状态分开：任务可为 `running / completed / needs_input / blocked / cancelled / failed`；提议可为 `pending / partially_applied / applied / rejected / conflicted`。`completed + pending` 表示已交付、待审阅；只有写入成功才显示已修改。

## 6. 权限与授权范围

| 能力 | 只读 | 审阅修改 | 自动修改 |
| --- | --- | --- | --- |
| 读取允许的本书上下文 | 允许 | 允许 | 允许 |
| 交付可应用提议 | 禁止；可给文字建议 | 允许 | 允许 |
| 写入当前授权目标 | 禁止 | 作者采用后 | 校验通过后 |
| 改其他章节／设定／大纲 | 禁止 | 先授权相应范围 | 先授权相应范围 |
| 服务器文件、命令、全局配置 | 不开放 | 不开放 | 不开放 |

读取本书参考和改写当前章节可以同时成立，不能把“能读”当作“能写”。附件引用也不授予修改附件或关联实体的权限。

建议新增共享策略契约，包含 `policyId、revision、sessionId、bookId、mode、readScope、writeScope、expiresAt`。写范围用章节／条目 ID 和领域表示，不把模型生成的名称当作授权目标。

- 策略由前端明确操作建立，服务端绑定现有浏览器 capability 与会话；模型参数不能创建或扩大授权。
- 服务端工具注册及执行都检查权限，前端实际提交事务再检查一次当前策略。
- 修改权限增加 revision；在途任务交付旧 revision 的自动修改不得写入，可保留为待审阅。
- 换书、删除会话、撤销授权立即关闭旧任务自动应用资格。仅收起面板不等于停止任务。
- 新会话和重新载入不静默继承扩大后的自动授权；可记住 UI 偏好，但授权需重新建立。
- 公网仍是浏览器 capability 隔离，不能将它描述为用户账户权限系统；服务端无法证明任意 bookId 的真实所有者，前端本地归属校验仍必需。

## 7. 编辑提议与持久化

### 7.1 沿用的基础

复用 `shared/assistantEditProposal.js`、`assistantEditTransaction.js` 和 `assistantEditJournal.js`，继续使用同一正文存储及事务回执。当前协议最多 8 处、24 KB，支持 replace/append/create；整个字段基线保护可靠但较粗，不能把现状写成已有逐段差异引擎。

### 7.2 协议升级建议

提议增加 `schemaVersion、proposalId、runId、policyRevision、changes[]`；每处增加稳定 `changeId、groupId、dependsOn、target、anchor、before、after`。目标保留领域、对象 ID、字段；锚点优先使用现有正文单元 ID、文本范围和校验指纹，附带邻近文本帮助定位。

处理规则：

1. replace/delete 必须证明旧文本仍对应目标；多个同文段落不能任选其一。
2. append 明确章节尾还是具体插入点，不能将所有续写都追加到全章末尾。
3. delete 作为明确操作允许空 after；不靠放松所有空文本校验实现。
4. 同一字段可包含多个互不重叠修改；重叠修改拒绝或先合并为一处。
5. 无依赖的修改支持逐处采用；创建角色再引用等有关联的改动形成原子组，不能拆出无效状态。
6. 采用一处后推进同组剩余锚点和基线，避免正常的部分采用导致全部后续冲突。
7. 正文有无关编辑时，仅在位置映射和指纹可证明正确时继续；不能证明则保留候选并报冲突。
8. 旧提议兼容读取；缺少新锚点时沿用唯一 before 匹配与保守冲突保护，不猜测升级。

版本号、容量上限及迁移由共享契约统一管理。长章多处修改若超过限制，按有依赖关系的批次交付并报告未完成范围，禁止静默截断。

### 7.3 编辑器接入

`WritingNotebookEditor.vue` 已有 ProseMirror decoration 和光标补全逻辑。稳定的 Agent 修改应有独立的提议展示状态，不能直接套用会随光标离开而消失的即时补全状态。

将定位、差异展示和选择处理放入有边界的模块，`Authoring.vue` 只负责装配。提议装饰不能进入序列化正文、字数或自动保存。切章节后可回到待审阅位置，刷新可恢复候选及处理结果。

“撤销本次”依照回执撤销已采用部分；若作者之后又修改同一区域，先报冲突，不覆盖后写内容。编辑器 Ctrl+Z 和事务撤销需统一历史边界，不能让界面撤销但持久化仍保持新值。

存储失败必须恢复内存、编辑器和持久化的一致状态。现有多键日志不是跨标签页互斥锁；需增加单次应用幂等与跨标签页协调，避免两个窗口重复应用同一提议。

## 8. 接口分工

以下保留设计契约；现行落点见实施记录。实际已沿用 run/resume 与 SSE，新增策略操作和完成工具。

| 接口／位置 | 输入或输出 | 责任 |
| --- | --- | --- |
| 共享权限契约（新增） | 权限枚举、范围、revision、有效期 | 前后端一致校验 |
| `/api/storyagent` 下会话策略操作（新增，路由名实现时统一） | 建立／更新／撤销策略，返回服务端认可 revision | capability 绑定、目标范围与撤销 |
| 现有 run/resume | task intent、policyId/revision、book/chapter、选区与正文快照版本 | 固定任务目标；权限不从模型输出读取 |
| `submit_edit_proposals` | 版本化提议，返回可交付 ID 或明确拒绝原因 | 权限、形状、目标与基线校验；工具本身不直接写正文 |
| 现有 SSE / 最终结果 | runId、事件顺序、outcome、proposalIds、实际工具结果 | 流式显示与结束语义一致 |
| 前端提议管理 | review/apply/reject/undo，含 group/change ID | 处理状态、事务、幂等和 UI 联动 |
| 共享现场服务 | 获取已确认快照、标脏、按需识别、确认候选 | 推演与其他入口复用同一数据 |

写入链固定为：模型交付 → 共享校验 → 形成待审阅提议 → 作者确认或有效自动授权 → 事务写入 → 回执。前端提议管理是正文唯一应用入口，避免工具结果、SSE 完成回调和消息恢复分别写一次。

SSE 重放、重复完成事件、重连和迟到返回以 `runId + proposalId + changeId` 去重；只接受当前书和策略下的应用资格。旧任务结果可以留在所属会话查看，不能落到当前打开的另一本书。

## 9. 现场识别与频繁更新

共享场景数据继续由现有 `useAuthoringSceneRecognition`、`useAuthoringSceneWorkflow`、`useAuthoringSceneLaboratoryWorkflow` 及对应服务管理。合并的是入口和布局。

- 输入正文只标记版本变化，不逐字调用模型或刷新人物列表。
- 首次推演、使用需要现场的能力时，对过期快照识别一次；另保留手动刷新。
- 缓存键包含书、章节、正文版本、识别策略和文本指纹；相同请求合并在途调用，限制缓存数量。
- 采用助手修改或推演草稿后标记过期；未采用草稿不进入识别输入。
- 识别结果是候选，展示新增／离场和依据，作者确认后更新当前场。已有确认不能被下一轮猜测覆盖。
- 异步返回重新核对书、正文版本和请求归属；切书、撤销或新请求后迟到结果不写入。
- 识别失败保留已有确认与本次草稿，允许作者手工调整后继续，不清空生成文本，不强迫重新生成全文。
- 一章可能多场，一个场也可能跨段落；不能用“章节 ID 等于场景 ID”的简化模型覆盖原数据。

## 10. 实施顺序与交付条件

| 阶段 | 工作 | 可以进入下一阶段的条件 |
| --- | --- | --- |
| P0 基线与运行包 | 记录当前会话、提议与事件形状；保护本地修改；确定运行包源码修复位置 | 复现两次查设定却不提交修改；能安全构建候选运行包 |
| P1 任务协议及基础权限 | 修初始/resume 提示和完成判定；只读／审阅范围在服务端与写入端生效 | 连续对话自然请求能交付提议，缺失提议不再假完成 |
| P2 原位审阅 | 提议版本、锚点、逐处／分组应用、冲突和恢复；接正文与现有设定面板 | 作者能定位、接受、拒绝、撤销，刷新后状态一致 |
| P3 自动修改 | 授权生命周期、撤销、幂等、保存失败保护；接菜单和范围 UI | 正向与越权场景均验证通过才显示自动模式 |
| P4 现场与工具轨 | 当前场嵌入推演；旧入口跳转；按需识别与确认；整理分组 | 原现场能力均可达，独立入口可安全移除 |
| P5 组合体验 | 整理文案、浮层、亮暗材质、窄屏；自然语言真实模型验收 | 全链路回执、实页截图与已知边界齐全 |

每阶段限定改动范围。先做输入区菜单、稿面一处差异、推演当前场三张代表性视觉切片，再扩展状态；遵循 [视觉对齐流程](../engineering/visual-alignment-workflow.md)，不要先重写整页再验收。

### 运行包构建前的特别处理

当前构建脚本会重建 `.runtime/storyagent`，而用户任务日志可能正在其内部。P0 必须先将任务持久化目录迁至独立稳定数据目录，做迁移、兼容读取和回滚；不得直接删除当前运行目录丢失会话。

运行时修复采用上游固定 SHA 或受控扩展，新增扩展文件全部纳入构建摘要与一致性校验。确认部署要求的 Node 版本和实际运行版本；在隔离目录构建候选包，不重启用户实例。更新现有运行包文档，不仅记录本机临时修补步骤。

## 11. 验收清单

实施时将回归合入既有测试，遵守核心 20 文件／200 用例上限；专项浏览器流程放入显式 smoke 脚本。不能仅凭按钮存在或源码字符串匹配宣称链路完成。

| 类别 | 必须覆盖的操作和结果 |
| --- | --- |
| 连续对话 | 先讨论几个方向，再说“试试第一条”；不额外提示工具名，也能提交对应续写提议 |
| 无修改请求 | 询问设定、讨论剧情只回答，不凭权限模式擅自改稿 |
| 错误完成 | 模型只输出正文、工具报错、预算不足均不能显示已修改 |
| 正文定位 | 选区改写、章尾续写、重复段落、多处修改、跨章节定位准确 |
| 权限 | 只读不能交付可应用写入；越范围调用被拒；模型伪造策略无效 |
| 在途授权 | 生成中撤销自动权限、换书、删除会话，迟到结果不写入 |
| 审阅 | 单处、整组、依赖组、部分拒绝、刷新恢复处理状态 |
| 冲突 | 无关编辑可证明则保留；同段编辑、对象删除、基线失效明确阻断 |
| 保存与撤销 | 存储拒绝、部分失败、刷新恢复、Ctrl+Z、事务撤销一致 |
| 重复事件 | SSE 重放、重连、双窗口、双击采用均不重复写入 |
| 多领域 | 正文、设定、大纲在原有位置审阅，人物和世界书归属不串书 |
| 现场 | 使用时识别一次、同请求合并、作者确认入场、手动刷新、失败保留稿件 |
| 现场来源 | 已采用的助手和推演文本可更新识别；未采用候选不会进入事实 |
| 推演回归 | 空指令可按正文继续；生成后可接受/拒绝，场景检查不反复清空草稿 |
| 视觉 | 1440、1024、390 宽度，亮暗模式，页面缩放、长菜单、滚动与软键盘 |
| 交互 | 权限浮层对齐触发点；加号不挡输入；键盘、焦点和悬浮说明可用 |
| 运行包 | 可重复构建，源码与摘要对应，任务日志迁移/回滚不丢数据 |

实际模型验收使用隔离测试书，包含一次“讨论 → 续写 → 部分接受 → 继续修改”和一次受限自动修改。记录真实工具名、目标、应用回执和最终正文变化；不能用伪造提议替代真实模型链路。临时截图看完清理，不改用户作品。

实施交付时运行仓库完整门禁，记录命令、退出码和测试预算，并单独记录浏览器与真实模型证据。门禁通过不等于视觉已获作者确认。最终更新 PLAN、LOG、STATUS 与现行架构文档，发布仍遵循 main → server-version 的独立流程。

## 12. 参考与完成定义

参考 VS Code 官方 [审阅 Agent 修改](https://code.visualstudio.com/docs/agents/run/review-code-edits) 与 [审批及权限](https://code.visualstudio.com/docs/agents/run/approvals)。借鉴原位差异、逐处处理、范围授权及撤销。不同 VS Code Agent 类型的落盘和审阅行为有区别，Pinax 按浏览器本地正文存储实现自己的明确约定，不照搬终端、工作树或代码文件操作。

这轮完成意味着：**自然语言修改请求确实产生可定位的修改；作者清楚助手能改哪里；每次写入可追踪和撤销；当前场在推演里直接管理；旧功能仍能找到和使用。** 仅菜单更名、增加权限字段或把生成文字换个位置展示，都不算完成。
