# 人物、规则与命运试演：现状核对和最小原型建议

日期：2026-09-08。状态：调研与候选建议，尚未授权实施。

上位路线：[产品整合主计划](./pinax-integrated-product-roadmap.md)的设定、历史/世界状态与按需上下文方向；体验入口沿用[UI/UX 与故事试演计划](./authoring-ux-and-story-play-plan-20260905.md)，数据语义衔接[设定／历史只读能力支线](./authoring-parallel-foundation-plan-20260905.md)。本文不改变既有交付优先级。

## 1. 结论与证据边界

推荐先验证“同一个人物，只改变一条信念，比较他在同一场景里的选择”，再验证两条明确能力，最后探索选择性记忆继承与世界内回溯。

目前 Pinax 有当前场、带依据的方向候选、文本排演、可编辑草稿和受控采用链。主要缺口是“人物尝试了什么 → 规则如何裁决 → 实际发生什么”的明确记录，以及角色信息、故事时间、循环经历的语义隔离。继续增加生成字数或能力名称不能代替这些能力。

本报告基于用户提供的《Pinax 趣味性机制调研：从〈Re:Zero〉到可推演的人物与命运》及当前工作树源码阅读。参考作品提供玩法启发，不证明产品效果；本文没有重新逐项核验该报告的十八项外部来源。源码位置证明实现存在，不证明其真实模型效果、全部分支安全性或线上版本状态。本轮未执行真实模型、浏览器旅程或 Livid 性能实验。

审查对象为 `integration/consolidation-20260823` 的混合工作树，包含未提交修改；未来实施前必须重新核对实际基线，不能把本文当成 main 或生产部署清单。下列缺失项表示在所查链路中未找到完整支持，不声称全仓不存在相关局部机制。

## 2. 必须保持的玩法语义

- 作者修订：改变稿件或设定版本，被舍弃内容通常不成为角色经历。
- IF 试演：从同一背景探索另一条件，结果仅属于该次试验，确认前不进入正式稿件或世界状态。
- 世界内回溯：世界恢复到故事过去，指定角色获准保留指定经历；物品、关系、任务与记忆分别遵守继承策略。
- 倒叙补写：揭示过去已经发生的准备，不能静默推翻既成事实。

故事时间、作者修订时间、角色经历顺序分别记录；世界事实、角色观察/记忆、信念和对外说法分别解释。“甲说了 P”不等于 P 成立，“甲上一轮见过 P”不等于本轮已发生 P。

硬规则、软倾向和作者主题目标不能混为一谈。规则卡需区分自然语言说明、模型辅助判断和真正可以确定执行的部分；冲突或信息不足应明确呈现。性格允许在动机与经历支持下改变，不把违背倾向一律判错。关系优先保留方向与具体事件，不默认归一为好感数值。

### 3.1 实际链路不能混用

Authoring 场景方向经冻结上下文进入方向规划，再选择方向生成正文草稿，经审阅采用。改变条件则经 intervention session、证据与目标范围冻结，生成目标替换稿，最后采用。后者的结果对象主要表达文本，不提供已裁决的行动事件账本。

旧体验通过 gameStore 回合、消息祖先链、runtime 快照和记忆候选过滤管理分支。它有状态恢复基础，但未证明可直接承担 Authoring 的长期 IF 世界或死亡回归。

生产正文的工具目录与授权还受 [narrativeKernel.js](../../src/services/agents/narrativeKernel.js) 和 [manifestToolAuthorization.js](../../src/services/agents/context/manifestToolAuthorization.js) 限制。通用 registry 中存在历史或地理工具，不代表 Authoring 已获准读取完整历史与世界状态。原型不得绕过该边界把全量状态交给模型。

### 3.2 与 K 线的关系

K 线已规划身份、事实、时间、可见性和带来源查询；上次核对当前 `src/services/project/` 未见该计划拟新增的 `knowledgeReadModel/`，不能把计划当实现。首个小场景可使用显式合成输入验证玩法；长期角色视角、跨循环记忆与历史查询应衔接 K 线，不复制另一份世界知识库。

## 4. 三个候选原型

| 原型 | 作者体验 | 复用与最小新增 | 最大风险与裁剪理由 |
| --- | --- | --- | --- |
| 只改一条信念（推荐） | 同一人物面对同一问题，选择及其依据出现可理解差异 | 复用当前场、方向、Ghost 和采用；新增同基线 A/B 临时覆盖、行动与变化提议、对照呈现 | 随机差异冒充信念作用；先限定一个条件和一个关键事件，无需完整规则引擎 |
| 两条能力，一次裁决 | 测谎与动物交流改变沟通和调查的可能性 | 复用角色资料、草稿审阅；新增两条明确能力条件和作者确认的行动结果 | 模型扩大能力范围、人工操作过重；只做两条规则，无需通用 DSL |
| 上一轮的一段记忆 | 甲保留亲密经历，乙却仍是陌生或警惕状态 | 借鉴旧体验快照与分支过滤；新增继承名单、记忆归属、逐角色输入与循环标记 | 共享摘要、旧任务或全局事实泄漏；限一个回溯点、一段记忆，不做无限循环 |

推荐依次验证，不把三项自动立项。若第一项没有可感知行为收益，先修正人物推演，不继续叠加权能或数值。

## 5. 推荐样例：生日下午，守诺的两种理解

### 5.1 固定初始情境

三个人在同一地点。寿星明确说过不喜欢被当面欺骗；甲答应乙，在约定时刻前不透露生日安排；寿星现在问甲：“你们是不是在瞒着我准备什么？”人物位置、承诺、知情范围、时间和目标固定。

只改变甲的一条软信念：

- A：“答应别人的事，未经对方同意不能改变。”
- B：“承诺若伤害了当事人的选择权，就应该重新协商。”

不预写结局。甲可回避、暂停、请求乙协商或提出其他行动；B 不必坦白，寿星不必愤怒或原谅。同一行动也可能由不同依据支持。

本样例暂不启用测谎、动物交流或回溯，以隔离信念对选择的影响。保留日常、合作和温暖的结果空间，避免把冲突升级当成唯一趣味来源。

### 5.2 用户操作与可观察结果

1. 在当前场选中甲，打开仅用于本次试演的信念修改。
2. 显示唯一变化，固定初始快照，分别运行 A/B。试验条件不得覆盖正式角色卡。
3. 模型先提出下一项关键行动、显式信息依据和可能变化，在关键选择处暂停。
4. 作者确认模糊结果后，生成与已确认行动相符的正文草稿。
5. 比较行动、说法、承诺处理、信息变化及待确认关系变化，再采用所需正文。

比较依据来自正文生成前的提议和作者确认记录，不从最终两段文本事后补写理由。不展示模型内部推理；展示已提供事实、显式理由和确认状态。

### 5.3 最小新增与实现约束

以下是拟议职责，不是现有模块名：

- 同基线试验记录：初始输入及 revision、唯一变量、模型配置、请求/输出和 A/B 归属；首版允许只在当前试验会话保留，并明确关闭行为。
- 临时条件覆盖：生成时明确替代指定信念，不能同时把新旧信念以同等事实输入；正式世界书仍保持原值。
- 行动与变化提议：绑定已有实体、证据及本次试验身份，区分预测、作者确认与未确定结果。
- 对照展示：先看实际行动与已确认变化，再看正文；采用继续复用现有事务链。

优先延伸既有任务调度和上下文合同，具体写集须在实施时追踪消费者后确定。无需新建角色 Agent 层级、数据库、脚本运行时或完整长期分支树。

第一版是作者参与裁决的半自动试演。人物心理和关系变化不能靠代码结构校验宣称已经成立。正文采用、正式角色信念修改、世界状态确认继续是不同操作。

### 5.4 最小验收与继续条件

| 案例 | 验收要求 |
| --- | --- |
| 单变量对照 | A/B 起始输入只有指定信念不同，人物位置、时间和消息未暗改 |
| 正式数据隔离 | 编辑试验、取消、放弃、切书和迟到结果不修改正式资料；采用正文不自动覆盖信念或关系 |
| 信息范围 | 不凭空引用未提供秘密；检测或作者发现越知后拒绝/纠正提议，不以一次通过宣称完整认知隔离 |
| 行为差异 | 比较具体选择及依据，提到信念次数不作为成功指标；允许相同选择 |
| 结果来源 | 对照能追到行动提议和确认记录，预测不伪装成已发生事件 |
| 原文一致 | 正文不得静默推翻确认结果；矛盾结果进入修订而非直接采用 |
| 偶然性控制 | 同条件少量重复，记录模型配置、输入和输出；固定种子不承诺模型完全复现 |
| 趣味性 | 作者是否主动再改一个条件、再试一次或使用结果，由真实反馈判断，不由模型自评分 |

建议保留普通提示词基线与最小结构化试演对照。若结果只是换文案、人物像执行指令、操作负担超过收益，则缩减约束并调整体验，暂不扩大机制数量。

## 6. 回溯原型前的额外门槛

需要明确世界恢复源与经历继承源是两件事。指定角色只能得到获准继承的记忆，不能直接查询整个旧分支。关系分别按方向恢复，上一轮事实带循环来源，不能自动成为本轮事实。

必须额外验证：旧计划/延迟效果/在途生成取消、检索与摘要失效、任务身份变更、过期能力不生效、冲突规则暂停。快照存在、一次读档成功不代表上述全部成立。

倒叙补写若与既成事实冲突，应转为作者修订或 IF 建议；不能以“回溯”名义混用。长程事件账本、能力规则优先级和更完整关系模型按实际需要后置。

## 7. Livid 与动态脚本的定位

本组原型不需要解释器。当前工具已有批量 ID 查询、过滤、缓存和同轮并行；普通算式也有受限复算路径。首先需要明确数据与可检查规则。

当真实任务反复需要不同的多步组合，例如批量比较人物行程、信息传播与条件变化，再比较现有 tools、固定批量工具和动态脚本。三者使用相同证据、权限及底层调用预算，脚本内部调用也计数。

Livid 可以作为可替换实验后端。当前本机 C++ 解释器已有 AST、作用域、函数与 `Callable` 宿主接口；仍需结构化数据桥、资源预算、取消、任务隔离及异步宿主调用支持。自研语言不天然构成安全沙箱，也不能解决事实缺失。已有语言方案与 Livid 应消费同一接口，以准确性、往返、总 token、耗时和维护成本决定采用。

## 8. 实施前的产品决策

尚待实施指令及以下语义确认；本报告不替作者作最终决定：

1. 首版是否接受作者确认模糊行动结果？建议接受，以半自动方式先验证趣味性。
2. 首版是否只采用正文，关系、经历、信念变化另行确认？建议保持分开。
3. 进入回溯阶段后，由作者主动触发还是世界事件自动触发？此项可延后，但会影响任务取消与提交边界。

下一实施指令应明确选中的原型与写集；当前不新增依赖、不迁移数据、不启动 worker 或付费模型。既有 U 体验实现和 K 只读能力计划继续按各自安排推进。

## 10. 扩展调研：一切皆文件、速记底层与空间／异世界

本节追加于 2026-09-08。问题来自用户提出的“速记下面再加一层，一切皆文件，空间和异世界也能这样抽象”。以下结合当前源码与一手资料提出设计建议，不是已有实现说明，也不自动替换第 5 节的推荐原型。

### 10.1 结论：可以统一对象入口，不能用文件操作代替世界规则

这个方向有实际价值：先随手写下一个想法，之后逐渐为它补上类型、引用、空间关系和规则，让同一份资料进入角色、设定、当前场与推演。创作者不必一开始填完复杂表单，也不必在每个功能里重新复制一份描述。

更准确的工程目标是“创作对象有统一身份和访问方式”，而不是“所有数据都必须保存成一个 Markdown 文件”。需要分开三层：

| 层 | 对作者／系统的意义 | 不应混淆 |
| --- | --- | --- |
| 文件式操作界面 | 新建、命名、搜索、分类、链接、打开详情 | 文件夹只是整理视图，不自动代表故事里的包含关系 |
| 有类型的创作对象 | 稳定身份、描述、来源、类型能力、与其他对象的关系 | 相同外壳不意味着角色、正文、图片和空间共用全部字段或写入方式 |
| 物理持久化 | 浏览器存储、桌面文件、索引与事务 | 磁盘路径不是人物身份，保存文件不是故事事件 |

因此，空间卡可以像文件一样编辑和引用；角色“进入空间”却必须是一项有条件、有结果的故事动作。改文件名不改变人物身份，移动目录不传送人物，删除资料不杀死角色，复制资料也不默认制造一个平行世界。

### 10.2 成熟系统分别提供了什么参照

以下来源本轮已访问。只借鉴其明确支持的机制，不声称它们已经实现 Pinax 所需的叙事模拟。

| 参考 | 已确认的机制 | 对 Pinax 的设计启示与边界 |
| --- | --- | --- |
| Obsidian | 笔记支持内部链接；文件改名可更新内部链接，行为受设置控制 | 文件式编辑和互相引用适合资料管理，但路径维护本身不是故事实体消歧。[内部链接文档](https://obsidian.md/help/links) |
| Obsidian Properties | 文件头可保存 YAML 属性，包含文本、列表、数值、日期及链接等 | 自由正文可以逐步附加结构，不必把速记立刻变成表单；属性存在不代表其中规则已经能够执行。[属性文档](https://obsidian.md/help/properties) |
| Anytype | 对象有名称、类型、属性和正文，通过 space/object ID 访问；归档与恢复属于内容管理 | 可以统一对象操作而保留不同类型；这里的工作空间不能直接等同故事里的异世界。[官方对象 API 指南](https://developers.anytype.io/docs/guides/get-started/objects/) |
| Inform 6 Designer’s Manual | 门作为对象连接地点，具有开关、锁定等状态；通行可受动作处理及目的地逻辑约束 | 空间不一定从地图坐标开始，可以先表达地点与可通行连接；链接存在不意味着角色一定能通过。[§13 Doors](https://inform-fiction.org/manual/html/s13.html) |

综合建议是：借鉴笔记系统的低门槛输入、对象系统的稳定引用、互动小说系统的地点和动作语义。不是整体引入其中某个框架，也不据此要求自研解释器。

### 10.3 Pinax 当前可以复用什么

| 当前结构与代码位置 | 本轮查到的事实 | 对该方向的影响 |
| --- | --- | --- |
| [authoringDocumentRepository.js](../../src/services/writing/authoringDocumentRepository.js) | 文档角色只有 `exploration / manuscript`；前者存在 `book.explorationDocuments[]`，后者沿用章节；handle 包含项目、角色、文档身份与 revision | 有统一编辑文档入口，但不是角色／空间的通用对象仓储 |
| 同文件的 exploration 规范化与保存 | 有标题、内容、状态、来源引用、批注、revision；规范化选取已支持字段；保存递增版本 | 不能把任意 `realm` 字段塞进对象就宣称接入；还需读写适配、校验和消费者支持，revision 递增也不等于并发条件写入 |
| [Notes.vue](../../src/pages/Notes.vue) 的 `confirmCreateNote` | 有 `bookId` 的文字新建进入 exploration，记录 `materials:text-capture` 来源；无该上下文时进入 narrative asset | “速记”是入口概念，背后已经有不同归属，不宜另建一套全部接管的速记数据库 |
| [writingNotes.js](../../src/services/writingNotes.js) | 还保留独立 `WRITING_NOTES` 数组及素材转笔记路径 | 旧笔记与当前项目探索稿不能按标题直接合并；后续需识别真实来源类型 |
| [writingBooksRepository.js](../../src/services/writing/writingBooksRepository.js) | 书记录绑定一个 `worldbookId` | 世界书是资料容器，不等于一个故事宇宙；人物穿越不应靠切换整本书的世界书绑定实现 |
| [worldStore.js](../../src/stores/worldStore.js) | 世界书条目已有类型、分组及结构化派生／用户修改保护逻辑 | 角色、地点继续由现有资料所有者写入；文件夹分组不应被重新解释为物理位置 |
| [projectKnowledgeFacade.js](../../src/services/project/projectKnowledgeFacade.js) | 通过 readers 按种类解析资料，整理来源与 authority | 可作为统一读取的衔接点；它不是统一写库，也不独自提供角色可见性授权 |
| [placeIdentity.ts](../../src/services/world-map/model/placeIdentity.ts) | 区分稳定地点 `worldbookId + worldbookEntryId`、版本化地图对象、稿件场景出现 | 已支持“地点不是地图上的一个图形”；无需为了口袋空间先生成一张地图 |
| [桌面 foundation schema](../../electron/projects/migrations/001-foundation.sql) 与 [projectRepository.mjs](../../electron/projects/projectRepository.mjs) | 有 item ID、相对路径、revision、内容 hash 和分阶段文件事务；item kind 当前限 volume/chapter/reference | 可以借鉴文件身份与事务，不代表浏览器数据已经落盘，也不代表桌面已经支持 realm 类型和完整 Authoring 接线 |

结论：已有足够的文档、地点身份和只读适配基础开展小实验；缺的是跨类型对象引用约定，以及空间的运行时语义。不是“从零造一套文件系统”，也不是“底层都是文件所以只需换 UI”。

### 10.4 底层新增层应该有多薄

建议先做现有仓储之上的逻辑对象引用和适配协议，而不是第二个可写的统一数据库。下面是拟议职责，不是现有 API：

- 身份：对象来自哪个项目／资料容器、哪个现有 owner、哪个原生 ID；标题与路径只用于展示和定位。
- 类型：说明能否编辑正文、作为角色引用、作为地点引用、参与规则检查；不把未知类型默认为世界事实。
- 内容与来源：正文仍留在原仓储，引用能指向来源对象、来源版本及必要片段。
- 版本：读取当前资料可跟随最新版本，固定试验必须记录当时依赖；两种引用行为不能隐式混用。
- 操作：通用入口把修改分派给原 owner 的受控写入链；不直接跨越世界书审阅、正文采用或 manifest 授权。

新层应优先返回引用、摘要和能力描述，按需读取正文；不复制全部正文组成一个“更方便的总库”。派生索引可以重建，正式资料仍只有明确的写入所有者。对象统一不要求编辑器完全一样：角色保留角色卡，空间保留设定正文，图片保留媒体资源。

同名不是同一对象。两名“林舟”可以共存，改名仍保留身份；同一角色出现在多张地图、多个章节时，也不应产生新的角色实体。跨作品是否共享同一人物设定需要明确引用或复制，不能仅凭同一个世界书 ID 就默认共享全部运行状态。

### 10.5 从速记成为正式对象：渐进整理，不是自动改类型

例子：速记写下“阿禾有一枚戒指，里面是一间雨停不了的小屋，只能带走自己亲手放进去的东西”。这段文本至少包含人物、物品、空间、进入关系和取出限制，不能直接把整段当成对象名称，更不能默认一段速记只对应一张卡。

建议流程：保留原速记 → 提出对象及关系候选 → 作者确认新建或链接已有对象 → 在对应 owner 内创建／更新 → 保留来源引用。名称候选与正文内容分别展示；“主角”“配角”只能作为分类，不自动充当人名。无法确定指代时保留待确认，不以模型猜测完成实体合并。

默认采用“从笔记提炼对象”：原笔记与新角色／空间具有不同身份，通过来源关联；一份笔记可以提炼多个对象，一个对象可以引用多份笔记。再次提炼应提示已有结果或追加候选，不重复建卡。后续修改笔记不自动覆盖已经审核的设定，修改设定也不回写歪曲原始笔记。

只有在作者明确说“这篇笔记就是这个地点的正式资料”、并且引用兼容策略已确定时，才考虑保留逻辑身份的类型升级。旧文档 handle 与新实体引用仍需明确适配，不能悄悄重解释已有链接。

这与“当前场从正文识别提到谁”是不同流程：前者建立和维护作者资料，后者定位场景中的出现与证据；后者发现一个名字，不意味着获准创建或改写正式角色。

### 10.6 空间、异世界、分支不是同一种容器

| 概念 | 例子 | 建议表达 |
| --- | --- | --- |
| 作者分类 | “异世界设定”文件夹 | 资料组织关系；移动不产生故事事件 |
| 空间包含 | 城市包含街区，小屋包含房间 | 带明确语义的地点关系；首版物理包含禁止自我或环形包含 |
| 空间连接 | 戒指入口连接小屋，门连接两间房 | 独立连接关系，可单向、关闭、有进入条件；不靠父目录表达 |
| 所有／控制 | 阿禾拥有戒指，乙持有它 | 所有权、携带和实际位置分别表达，互不自动推出 |
| 世界域 | 现实与镜中世界使用不同规则 | 为规则及空间范围提供边界，是否拥有独立时钟另行声明 |
| IF 分支／循环 | 同一小屋在另一选择后的状态 | 状态历史的范围，不默认在故事里存在可穿越入口 |

口袋空间可以先只是地点加入口，不必马上升级成完整异世界。只有确实需要独立规则、时间或跨域限制时才引入世界域。两个世界也可以完全没有连接；一个世界可以有很多地图；没有地图的地方仍然可以参与剧情。

人物穿越通常保留身份，只改变所在地点、可执行行动及可见信息。分身、平行同位体、灵魂投射是额外设定，不能从“复制文件”自动获得。梦境是否是真实共享空间、记忆空间能否带出物品，也必须由作者决定。

### 10.7 最小空间规则：先支持明确动作，不承诺任意自然语言可执行

一张空间资料卡在作者层可以包含任意描述；执行层首版只需支持已选场景用到的少量项目：地点身份、入口两端、当前开关、允许的动作及条件、退出方式。容量、距离、天气、时间倍率都不是每张卡必填项。

“进入”至少检查：人物当前在哪里、入口是否可达、入口是否打开、已声明条件是否满足、带入对象如何处理。返回可行、冲突或信息不足；未记载入口关闭不等于明确打开。条件依赖模糊心理、比喻或未知历史时，转为作者确认，不用字符串匹配冒充规则裁决。

“放入／取出”需要区分位置变化和所有权变化。一次转移应作为完整操作确认，失败不能让物品同时留在内外；重复提交同一动作不能复制物品。若当前写入链无法保证这点，实验先使用隔离状态并由作者确认，不提前接入正式状态。

戒指被交给别人、入口被毁、人物仍在空间内时，出口在哪里？这类结果不能由技术实现随意补齐。原型可直接禁止未定义操作并暂停；成熟后再按作者明确的规则裁决。故事世界里的“打开文件”“删除世界”即使是能力名称，也不授予模型真实文件系统权限。

### 10.8 时间与历史：不要把异世界理解为另一个存档目录

空间定义与空间状态应分开。定义说明“这里是什么、规则是什么”；状态说明“在这条历史的这个时刻，谁在这里、门开没开、物品在哪”。状态读取必须带已有项目／分支／时间范围，不能只凭地点 ID 找一个全局最新值。

第一版建议共用故事时钟，或由作者明确给出本次动作的时间，不支持独立倍率。当前 `writingTime` 和局部快照并不构成多世界时钟系统。

以后确实需要“里面一小时，外面一分钟”，至少要约定进入时的双边时间锚点、倍率有效区间、退出时的对应关系，以及定时效果按哪个时钟到期。倍率中途改变不能拿最后一个倍率回算整段经历；时间暂停和倒流更不能直接代入同一个普通比例公式。

嵌套空间也不能无限递归读取所有内容。空间包含、传送连接和时间映射分别处理；首版可以禁止未定义的嵌套和循环映射。规则修改若只影响未来，要记录生效范围；若要改变过去，应成为作者修订或新试验，不静默重写旧事件。

空间重置与人物记忆继承继续遵守第 6 节：位置、物品、承诺、旧任务、摘要和索引分别检查。普通对象版本历史不能替代世界快照，更不能自动成为角色所知。

### 10.9 与当前场、上下文和 Agent 的接线

建议作者从角色／设定查看完整资料，当前场只展示当前地点及相关入口、人物、物品和适用规则。展开某个文件夹不应把其中所有资料塞进上下文；有一条对象链接也不意味着 Agent 有权读取它。

一次空间行动可沿用“冻结输入 → 动作提议 → 条件检查／作者确认 → 结果记录 → 正文草稿”的职责划分。读取遵守现有 manifest 和后续 K 线的范围限制，显式记录本次采用的资料版本与来源。角色可见投影不能包含作者隐藏的出口、别人私有的记忆或另一分支的结果。

正式规则在生成期间变更、人物已移动、入口已关闭时，旧结果应标记失效或重新检查；不允许迟到文本覆盖新状态。正文采用仍与状态提交分开。如果作者只采用了描写，没有确认动作结果，界面不能显示“已经进入空间”。

图谱、关系表和对象 ID 只帮助定位证据，不会自动解决消歧、角色认知或剧情因果。可以让模型提出“这两处可能是同一房间”，但合并、越界读取和正式写入仍需原有权限与确认。

### 10.10 存储路线与工程取舍

| 路线 | 收益 | 代价／建议 |
| --- | --- | --- |
| 现有仓储 + 轻量对象适配 | 不迁移用户资料，复用角色／设定／探索稿与现有采用链 | 需显式处理不同 owner 的引用与版本；推荐用于首个验证 |
| 桌面文件 + 索引／事务 | 方便本地查看、导出和外部编辑；仓库已有部分基础 | 需处理外部改名、重复 ID、引用损坏、并发与崩溃恢复；不能仅为口袋空间提前完成全项目迁移 |
| 新建统一图数据库／对象数据库 | 可能简化大量跨对象查询 | 引入第二事实源、迁移和同步成本；当前缺口主要是语义与体验，暂不推荐 |
| 脚本／DSL 驱动全部空间 | 复杂动态规则可能复用代码 | 无法替代状态来源和裁决权限；先有重复出现的规则需求，再按第 7 节评估 |

文件可读写不等于多文件修改具有事务性。以后导出可用可读正文配合身份／引用元数据，但需明确哪部分是权威来源、哪部分只是可重建索引；不能维护两个都能独立改写的事实副本。媒体仍可以是独立资源，没必要转成巨大的文本字段。

### 10.11 最小验证：先让一个想法变成可引用的地方，再让它改变行动

以下是空间方向内部的两步，不是第 4 节之外同时开工的两条主线。若用户选择空间优先，再明确替代或插入当前原型的位置。

**第一步：速记 → 空间资料，不运行世界模拟。**

作者写“戒指中的小屋”，确认从笔记提炼一个地点并关联已有戒指。角色与空间标题可以改名，来源仍能打开；从设定和当前场入口查看的资料指向同一对象。初版不要求做通用文件管理器，也不要求把所有旧笔记迁走。

可观察价值：一个随手想法成为能被正文、人物和后续推演共同引用的正式资料，修改不需要到处复制。若这种转换比直接新建设定更麻烦，就先改善入口，不增加空间规则。

**第二步：一间小屋、一个入口、一次物品存取。**

限定一名人物、一件可携带物品、一个固定出口，使用共同时间；入口关闭时不能进入，进入后可把物品放下，退出再进入时物品仍在。放入不改变所有权。用隔离试验状态、明确动作记录及作者确认验证，不接无限嵌套、死亡回归或自动长篇推演。

随后只改变“入口当前是否打开”，从同一基线运行到下一关键行动。关闭时人物可以等待、求助或尝试别的办法，但不能由模型凭空穿门。对照展示实际选择和物品／位置变化，不仅显示两段不同文案。原型证明的是少数空间约束能否带来合理的行动差异，不是任意异世界已经可以模拟。

### 10.12 验收、停止条件与实施前选择

| 案例 | 预期边界 |
| --- | --- |
| 改名、换分类、地图重生成 | 原对象身份和引用保留；人物位置不变化 |
| 同名角色／地点 | 不自动合并；选择时能分辨来源和所属范围 |
| 一段速记包含多个实体、再次提炼 | 名称不吞掉全文；候选分别确认，不重复建卡或覆盖已审资料 |
| 修改来源笔记 | 正式设定不被静默覆盖，保留来源版本或变更提示 |
| 删除／归档资料 | 提示受影响引用，不编造人物死亡、空间坍塌或清空历史 |
| 多作品复用资料 | 共享定义不等于共享位置、物品和分支状态 |
| 门关闭、条件未知、生成中规则改变 | 拒绝、待裁决或失效，不靠叙述绕过限制 |
| 转移失败、重复提交、取消及迟到结果 | 不丢失或复制物品，不提交半个动作，不污染正式状态 |
| 隐藏出口、别人记忆、旧循环事实 | 作者可见不等于角色可见，引用不可绕过授权 |
| 未支持的倍率／嵌套／梦境带出物品 | 明确未定义或人工裁决，不输出虚假的确定计算 |
| 采用正文 | 不自动创建已确认世界事件；文字与状态差异可识别 |

先用合成资料和确定性检查验证身份、引用、隔离，再做少量真实模型与作者体验对照。索引命中或结构校验通过，不算趣味性验证；要观察作者是否愿意继续改一个入口条件、关系或规则，再试另一种行动。

若实现需要同时迁移所有资料、重构数据库、接入完整多时钟或大量通用脚本才能看到第一次效果，应缩小原型。不能把基础设施规模当成玩法价值。

实施前真正需要选的是：先验证“速记变成可引用设定”还是“空间改变行动”；首个空间是否接受人工裁决及固定出口；试验状态何时、以什么方式获准成为正式事实。推荐先验证资料转换，再用隔离空间试验验证动作，不要求作者现在决定整个多宇宙架构。

最终判断：**“一切皆文件”适合作为统一创作入口；“有身份的对象 + 明确关系 + 有范围的状态变化”才是可推演空间的基础。** Pinax 可以沿现有结构渐进接近这个方向，但异世界的趣味来自规则如何改变人物行动，而不是目录树能装下多少世界。
