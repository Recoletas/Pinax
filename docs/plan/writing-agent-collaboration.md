# Pinax：资料导入与 Agent 工作流改进

本文用于外部贡献者了解现有实现、接入方向并提交 PR。范围集中在两项：**优化资料导入，完善 Agent 工作流**。产品方向、接入接口和前端由 Pinax 作者负责；贡献者按约定继续实现资料处理、文件操作、RAG 和 Agent 工作流。本文先确定能力边界，内部算法和模块实现由贡献者设计，接口调整先讨论确认。

现状依据：2026-09-29 的 Pinax `main@ebaebc5` 及当前源码审阅；不代表真实模型效果已经验收。

PR #4 后续沟通使用独立的[前端与接口说明](./pinax-agent-frontend-integration.md)作为附件，集中说明页面安排、能力输入输出、任务恢复及修改交付；本文保留现状和调研背景。

## 一、资料导入

### 当前实现

资料入口位于设定页。文件先在浏览器端解析，再保存来源文本和分块；后续可以查阅原文，或提取为世界书条目。

- 已支持 TXT、Markdown、PDF、DOCX、EPUB 的解析路径，包含编码识别、章节识别、解析报告及部分失败提示。
- 来源归档已有分块、章节定位和内容标识，并非只保存一段摘要。
- 世界书 AI 提取将输入组织成一次请求，生成设定、人物等条目，以及文风和示例字段，再进入预览和导入流程。
- 资料选取已有关键词匹配、关联条目和上下文预算限制；这是有限范围的参考片段选取，不能视为全文都已分析。

主要代码入口：

| 环节 | 现有位置 |
|---|---|
| 解析、章节识别与报告 | `src/services/worldbook/worldbookSourceAdapters.js`、`worldbookSourceParser.js` |
| 来源文本和分块归档 | `src/services/worldbook/worldbookSourceArchive.js` |
| AI 提取与导入工作流 | `src/services/worldbook/worldbookImportGeneration.js`、`src/services/agents/settings/settingsImportWorkflow.js` |
| 使用资料时的片段选取 | `src/services/worldbook/worldbookSourceSelection.js` |



### 已识别的问题

1. **长篇分析覆盖不足。** 当前世界书 AI 提取明确使用 `sourceText.slice(0, 12000)`，只处理传入文本的前 12,000 个字符。底层已有全文分块，但这一提取入口尚未形成逐块分析、跨块汇总的流程。
2. **提取与创作混在一起。** 现有提示词允许信息不足时“合理补全”，还要求产出规则、禁忌和文风条目。用于资料提取时，这会让原文事实与模型新增内容难以区分。
3. **结构化结果还需面向长篇整理。** 跨章节人物别名、重复条目、关系和事件应统一整理，并能追溯到原文；文件被解析成功不等于这些内容已被正确理解。
4. **更新和失败处理未形成统一的分析流程。** 解析报告、来源版本、记忆提取队列与缓存已有基础，需要让资料分析贯通这些能力，明确哪些部分处理完成、哪些失败或过期，支持继续处理和增量更新。
5. **文风目前主要是生成字段。** 尚缺从语料样本到可查看、可调整、可供写作任务使用的分析流程。

### 改进方向

- 在已有解析和归档基础上，完善长篇资料的分块分析与结果汇总，明确覆盖范围，减少遗漏和重复。
- 分离忠实提取与创作补全：提取结果附原文依据；推断或建议明确标注。
- 改善实体、别名和条目的整理，让作者能够审阅后进入现有设定或事实体系。
- 利用现有版本、缓存和任务能力处理重试与更新，避免每次重新分析全文。
- 将语料/文风分析作为资料导入的扩展用途，产出能被审稿和改写使用的特征、规则及例子。

这部分适合结合 NovelPedia 的长篇结构化和文风分析经验。具体采用哪些模块、如何分批处理，由方案和实际效果决定。

## 二、Agent 工作流

### 当前实现

Pinax 已有模型调用适配、任务分派、上下文组装和若干写作工作流，各入口的能力与执行方式尚不一致。

| 入口 | 已有行为 | 主要不足 |
|---|---|---|
| 资料问答助手 | 先收集授权证据，再请求模型回答，并检查来源版本 | 默认主要是一次请求，不能根据中间结果持续搜索、读取详情和补查 |
| 推演 | 根据现场和分支请求下一步；可按需调用 `history_lookup`，每步最多一次 | 查阅能力有限，后续状态核对与任务衔接需要完善 |
| 审稿与改写 | 已有写作方法、问题定位、修改建议、正文补丁和撤销 | 较长任务的查阅、检查、修改及恢复还需组织成连续流程 |
| 选区和批注 | 已有正文位置与局部操作入口 | 需要复用更完整的资料和写作能力，同时保持操作轻量 |

主要入口为 `useAuthoringKnowledgeAssistant.js`、`useAuthoringReviewWorkflow.js`，以及 `src/services/agents/authoring/` 下的查询会话、推演工具调用和写作方法模块。

### 改进方向

目标是让助手围绕作者的任务组织能力，而不是要求作者手动完成每次查阅与调用：

- 根据任务需要查资料、读原文、使用已有设定和记忆，再进行检查或改写。
- 将写作方法组织为可复用的工作流，明确输入、结果和需要作者介入的位置。
- 衔接任务状态、取消、失败恢复和结果采用，避免各入口重复实现执行逻辑。
- 作者明确授权修改时，可以在约定范围内自动改稿，并通过现有编辑链保留查看和撤销能力。

交互上继续保留三种方式：**助手承接较长的自动化任务，推演由作者参与关键选择，批注和选区操作保持轻量**。共享底层能力，不强制它们采用同一种交互流程。

这部分适合结合 Storyflow 的工作流和写作方法经验。SkillRouter 可用于后续能力增多时的选择与调度，是否引入由实际需要决定。

## 三、接入边界

| 方向 | 读取现有内容 | 返回给 Pinax |
|---|---|---|
| 资料导入与分析 | 已解析的资料、分块、来源版本、现有设定及作者的提取目标 | 带来源的结构化结果、文风分析，以及完成/失败/待复核情况 |
| Agent 工作流 | 作者目标、操作范围、正文、资料与记忆，以及现有模型和工具调用能力 | 回答、检查意见、推演结果或可定位的修改建议，以及任务状态 |

资料分析结果接回现有来源、世界书和事实流程；改稿结果接回现有编辑器提交与撤销流程。接入接口由 Pinax 侧确定，贡献者可以提出建议，讨论确认后调整，保持作品归属、来源版本及作者操作一致。

对外能力接口按以下四类衔接，具体字段由 Pinax 侧补充约定：

| 接口能力 | Pinax 侧传入 | 贡献者的实现返回 |
|---|---|---|
| 资料接入与处理 | 文件或已有文本、所属作品、来源版本、处理目标 | 可引用的资料、处理进度、分析候选、失败与更新情况 |
| 检索与原文读取 | 当前作品、查询目标、允许查阅的来源 | 相关片段、原文出处和定位、内容版本及覆盖限制 |
| 会话与任务执行 | 作品与会话、作者目标、正文范围和上下文 | 可关联到原任务的进度、等待选择、完成或失败状态，支持追问、取消和恢复 |
| 任务结果 | 本次任务的目标与操作范围 | 带定位和依据的回答、正文修改候选、设定修改候选或报告 |

前端根据结果类型决定展示位置，并通过 Pinax 的宿主服务完成资料保存、正文采用/撤销及设定确认。运行器交回候选和真实任务状态；界面切换不要求它重新开始任务。

## 五、PR #4 后续：世界书与文件管理的前端方向

2026-09-30 已只读查看 [PR #4](https://github.com/Recoletas/Pinax/pull/4) 的说明与差异。以下供双方讨论，尚未实施，也不是整份 PR 的验收结论。

### PR 当前实现

PR 增加 Node 适配器、pi-agent 任务循环、工具快照桥和任务转录落盘，并在前端新增独立的 StoryHarness-beta 面板，保留原助手。beta 已有会话、追问、条目提及和简单写作预设。

执行器实际调用 `pi-agent-core`；随 PR 带入的 Storyflow 内核快照按 README 说明仅供核对，当前运行不依赖它。因此不能将本次适配器描述为完整的 Storyflow flow 工作流已经接入。

目前 beta 从浏览器的当前世界书取前 30 条作为资源快照，不是对全部资料进行 RAG。适配器的文件落盘主要保存任务状态和转录，尚未接通作者的文件管理。面板输出也尚未进入正文采用/撤销流程；其技能预设目前将简短指令加入输入，不代表完整写作流程已经贯通。

这里的 RAG 指查找相关资料并将检索结果供模型生成时使用；数据库或索引是它的资料来源。Pinax 的 Utopia 式事实账本目前由浏览器 Dexie/IndexedDB 实现，并非已经连接外部 Utopia 数据库。后续可以把原文分块、世界书和已有账本作为检索来源，但本 PR 尚未实现这条接入。工具桥当前在请求携带的资源快照中做关键词搜索和按 ID 读取，既有文件导入仍由 Pinax 原有代码处理。

### 世界书：保留结构化编辑，让资料检索与设定使用衔接

现有世界书承担作者编辑人物、地点、关系和规则的功能，前端应继续保留条目编辑方式。原始资料与已确认设定需要能互相定位：作者从设定看到原文依据，也能从资料分析结果进入对应条目。

建议资料详情呈现原文、分析结果及处理状态。人物归一、条目补充和冲突作为待审结果，作者可以选择新增、合并或忽略。参考资料被检索到，并不意味着它自动成为本书设定。

RAG 在助手中表现为“按需要找资料、读取相关原文并标注出处”。作者可以显式提及一份资料、一个角色或一组条目，也可以让助手自行检索本书范围。引用能够打开原文位置；回答涉及已确认设定时，说明使用了哪条设定。导入覆盖和过期状态在资料页展示，避免只看到上传成功。

### 文件管理：围绕作品组织内容

建议按作品组织正文、资料和分析/生成结果，允许资料使用文件夹、标签或集合管理。前端的目录表示作者可操作的作品内容；浏览器版的逻辑目录与桌面版的实际文件夹可以由适配层映射。

首先确定文件读写归属：哪些内容由 Pinax 保存，哪些只是 Harness 的运行工件。两侧的文件引用应关联同一份内容及版本，防止修改一处后另一处继续使用旧副本。若需要同步到真实目录，应明确导入、更新和回写的关系。

助手生成的检查报告可以保存为作品资料；改稿进入正文候选及差异查看；新设定进入世界书待审。作者能够打开、继续编辑或采用结果，临时任务文件则在任务详情中按需查看。

### 助手与工作流：一个作者入口，保留局部操作

独立 beta 适合作为接线验证入口。正式使用建议逐步接入现有助手，保留当前正文、选区、批注和推演位置作为任务上下文。

助手展示正在查阅、分析或修改的对象，提供停止、继续、引用及结果操作。详细工具记录和流程信息可以展开查看。多步任务不要求作者先编辑工作流图；批注、局部改写也不必都跳到长对话里。

diff 按结果类型衔接：正文显示目标处的修改前后和采用/撤销；设定显示条目变化并允许选择确认；新文件提供预览、保存位置和打开操作。明确授权自动改稿后，可以在限定范围内提交修改，结果仍需可查看、可撤销。

### 建议下一步讨论并接入的流程

先确定作品内容的保存与读写归属，以及 beta 向现有助手接入的方式，再打通：

> 导入一份长篇资料 → 查看处理进度和分析结果 → 确认部分设定 → 在助手中检索原文并引用 → 对选定正文提出修改 → 查看差异并采用或撤销。

前端交互以这一流程为依据，RAG、文件工具和工作流按需要接入。Node 适配器当前默认连接 `127.0.0.1:8451`；公网使用还需要确定它的部署位置，以及如何取得当前作品的数据，不能直接将本地连接方式视为公网接入完成。

## 六、助手全屏、检索呈现与空白书引导

2026-09-30 补充。作者明确提出：检索信息放在助手中；资料管理在现有资料页；正文修改在工作台；设定修改在工作台右侧设定栏；助手应有更明显的入口，并能引导空白书开始创作。以下保留调研后的产品方向；完整助手、空白书入口、引用预览和按作品保存的首版已本地实施，见[回执](../agent-runs/assistant-frontend-20260930.md)。新 RAG、文件管理和 Agent 工作流接口仍待接入。

### 当前前端的限制

调研时 `AuthoringKnowledgeAssistant.vue` 已在工作台右侧展示回答、缺失信息和原文依据；问答只存在页面内存，切书会清空，没有完整的助手开书入口。9 月 30 日的前端首版已补上完整页、构思入口和按作品保存；离开写作页仍会停止未完成查询，刷新不会自动重发。

这意味着助手全屏需要调整会话归属和任务衔接。只新增页面并重新挂载同一个组件，会丢失现有对话或中断请求；只放大 beta，则仍缺少作品、正文和结果采用的完整上下文。

本轮读取官方资料，并查看 Cursor 文件查看及 Sudowrite Story Bible 的官方桌面截图。没有进入这些产品的登录会话或核实其手机界面；下面的布局和流程是 Pinax 方案，不是对参考产品的逐项复刻。

### 一个助手，两种展示

建议在作品内部提供清楚的“工作台 / 助手”切换。助手全屏用于开书、讨论设定、资料研究、整章任务；工作台侧栏用于边写边问、选区修改和继续同一任务。两个展示共用会话、任务及结果，不形成两份聊天记录。

全屏页保留当前作品与返回工作台的入口。主要区域是对话、检索结果和任务进展；会话列表可以收起；资料原文或结果详情按需打开。没有详情时不常驻第三栏。

布局关系示意，非最终视觉稿：

```text
当前作品                         工作台 / 助手
-------------------------------------------------
可收起的会话列表 | 对话、任务与检索结果 | 按需详情
                 | 目标范围、输入与发送 |
```

回工作台时恢复原来的章节、选区和滚动位置，助手可以收在侧栏继续。同一会话的切换不重新发请求，不清空输入，也不把工作台中新选择的正文悄悄替换成本次任务的目标。新任务可以选择“全书 / 当前章 / 选区”，正在运行的任务保留启动时的范围。

会话以作品为归属。切书时呈现该书的会话和状态，返回原书能够找回。会话持久化与刷新后任务恢复分别处理：保留对话不代表后台一定还在执行；刷新后按真实任务状态恢复，不能自动重发原请求。

### 空白书怎样从助手开始

书库新建提供“和助手构思”以及“直接写作”，已有稿件继续走导入入口。选择助手后先建立作品归属，书名可以暂空，再进入助手页。无正文的新书在工作台空白区域提供明显的“让助手帮我开始”，作者已经直接写作或关闭引导后不反复弹回。

初始界面给一个输入框：“你想写一个什么故事？一句话、人物、场景或零散想法都可以。”少量起点包括“只有一个想法”“先想人物”“已有资料”“先写一个开场”，用于帮助表达目标，不要求先填完设定表。

助手从作者现有信息出发，一次解决一个决定：必要时问一两个关键问题，或提供少量方向供选择；可以随时跳到开篇，不要求按固定顺序完成世界观、人物、大纲。

例如作者说“想写一个失业调查员，在旧港查失踪案”：助手先围绕调查员的困境和失踪案的起点讨论；作者确定方向后，可选择整理人物、形成大纲或尝试开场。讨论中的备选设定保留为候选，实际写入设定或正文的动作明确可见。

形成可用的稿件或设定建议后，助手显示“查看正文草稿”“查看设定建议”等动作。进入工作台处理结果时保持这段会话，作者可以回来继续讨论。尚未生成内容时也允许随时进入工作台写作。

### 检索结果放在助手，原文管理放在资料页

助手的回答给出结论和引用，下面按需展开“找到的相关资料”：显示资料名称、章节或位置、相关原文及其与问题的关系。区分已确认设定、正文记录和参考材料；资料不足或尚未分析完成时说明覆盖限制。

点击引用可在当前助手中查看原文片段，再提供打开完整资料或定位正文的动作。窄屏在同一页面切换详情，不强行显示三栏。资料选择支持提及资料或条目，也可由助手按需查找；来源范围以本书为默认。

检索结果进入对话，不自动转换成设定候选。只有作者提出整理设定、更新条目等任务时，才产生对应的修改结果。助手上方的附件导入复用资料页的导入链，并能随后在资料页找到，不新增聊天专用的一套文件存储。

### 结果、进度与提醒

| 内容 | 主要展示位置 | 助手里的表示 |
|---|---|---|
| 检索信息、出处、讨论 | 助手 | 直接呈现并可追问 |
| 正文修改 | 工作台正文的候选/差异位置 | 说明改了哪些位置并提供定位动作 |
| 设定修改 | 工作台右侧设定栏 | 说明涉及哪些条目并提供查看动作 |
| 资料处理报告 | 资料页 | 完成摘要及打开报告动作 |
| 任务进度、等待作者选择、失败 | 所属助手会话 | 简短状态、停止、选择或重试；详细工具记录可展开 |

红点表示有新结果未查看，查看后清除；未处理的建议保留数量或明确状态，直到采用或忽略。完成提醒能定位到实际结果。失败应显示失败原因和重试动作，不能只留一个红点。

增加助手存在感主要依靠明确入口和可完成的任务；正文中仍保持既有批注和修改交互。运行中切到正文或资料只改变展示，不擅自取消任务；需要停止时使用明确的停止操作。

手机优先显示助手整页，对话与详情切换；进入正文、设定后保留返回原会话的入口。输入区考虑键盘和中文输入，长结果可阅读，控制信息收起。

### 双方下一步的交付

Pinax 侧确定并实现作品内的助手入口、全屏/侧栏切换、空白书引导、检索来源展示及结果定位。会话和任务状态与贡献者提供的接口衔接，原有问答、审稿和采用能力逐项接入。

贡献者继续完善资料导入与文件操作能力、RAG 检索和原文读取，以及 Agent 的多步执行、追问、取消和恢复；按接口提供来源、状态及可定位的候选结果。已有 beta 用于联调，正式前端由 Pinax 作者负责。

接口由 Pinax 侧确定作品、会话、任务目标、结果引用和状态等必要信息。前端负责选择展示位置及作者操作，运行器提供真实进展、来源和候选结果；贡献者有接口建议时先讨论后调整。

双方联调应覆盖：从一句想法进入助手；已有稿件仍能直接写作；运行中全屏与侧栏切换；打开原文后回到对话；正文及设定建议的采用/撤销；换书再回来；刷新恢复。桌面与手机布局、交互和截图验收由 Pinax 侧负责。
