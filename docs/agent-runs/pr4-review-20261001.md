## 需要修复

### 1. 作品归属仍取世界书 ID

[StoryAgentBetaPanel.vue:59](https://github.com/Recoletas/Pinax/blob/4f9bb707d2402efe28d3dc07dd9ab2b4297a2777/src/components/authoring/StoryAgentBetaPanel.vue#L59) 使用 `worldStore.activeWorldbookId` 作为 `bookId`。会话过滤和旧流守卫也依赖该值。

两本书共用世界书时，切书不会改变这个 ID，旧会话和输出仍属于当前面板；未绑定世界书的作品也没有独立归属。现有约定明确要求共享世界书的作品各有独立会话，见[接口说明](../plan/pinax-agent-frontend-integration.md#公共信息)。当前写作页已有真实 `selectedBookId`，应由 Pinax 传入作品 ID，并单独表达世界书绑定。

### 2. 首轮完成和载入会话后，继续发送仍会新建任务

[StoryAgentBetaPanel.vue:53](https://github.com/Recoletas/Pinax/blob/4f9bb707d2402efe28d3dc07dd9ab2b4297a2777/src/components/authoring/StoryAgentBetaPanel.vue#L53) 的 `activeTaskId` 是普通变量，下一行 `computed` 没有响应式依赖。

面板初开时，底部提示读取 `hasActiveTask` 并缓存为 false。之后完成首轮或载入历史会话，都不能使该计算值重新求值；[发送分支:307](https://github.com/Recoletas/Pinax/blob/4f9bb707d2402efe28d3dc07dd9ab2b4297a2777/src/components/authoring/StoryAgentBetaPanel.vue#L307) 继续走新建任务，无法携带此前转录追问。这是 PR 中原已有的问题，本次修订后仍存在。任务 ID 应成为响应式状态。

### 3. 运行中切书再取消，后端继续执行

A 书任务运行中，切到绑定另一世界书的 B。面板的[切书处理:286](https://github.com/Recoletas/Pinax/blob/4f9bb707d2402efe28d3dc07dd9ab2b4297a2777/src/components/authoring/StoryAgentBetaPanel.vue#L286) 清空 `activeTaskId`，却保留 `running` 和流控制器，取消按钮仍可点击。

[cancelTask:403](https://github.com/Recoletas/Pinax/blob/4f9bb707d2402efe28d3dc07dd9ab2b4297a2777/src/components/authoring/StoryAgentBetaPanel.vue#L403) 因 ID 为空跳过后端取消，只 abort 浏览器请求；[server.ts:85](https://github.com/Recoletas/Pinax/blob/4f9bb707d2402efe28d3dc07dd9ab2b4297a2777/adapters/pinax-adapter/src/server.ts#L85) 明确让断流任务继续执行。页面却提示「后端执行已停止」。需保留运行任务自身的 ID、作品归属和取消句柄，并根据后端确认展示取消状态。

### 4. 后端恢复允许把 A 书任务改归 B 书

[server.ts:129](https://github.com/Recoletas/Pinax/blob/4f9bb707d2402efe28d3dc07dd9ab2b4297a2777/adapters/pinax-adapter/src/server.ts#L129) 只在客户端漏发 `bookId` 时继承快照。若明确传入 B，服务端不会与原任务的 A 比较。

对 A 的已完成任务调用恢复，传 B 的作品 ID 和资料，会把 A 的历史转录与 B 的上下文混用，完成后还将同一任务落账为 B。此问题通过已有 bridge/API 即可触发，不依赖第 2 项前端缺陷。已有归属应保持不变，恢复请求归属不一致时应拒绝；历史未归属任务如何绑定另行明确。

### 5. 同一任务可同时恢复，取消句柄会被覆盖

[server.ts:124](https://github.com/Recoletas/Pinax/blob/4f9bb707d2402efe28d3dc07dd9ab2b4297a2777/adapters/pinax-adapter/src/server.ts#L124) 只有快照为 `running` 且 `active` 有记录时才拒绝恢复。恢复启动后并未追加 `running` 快照。

两个窗口先后恢复同一个已完成任务，第一轮未结束时，第二轮仍读到 `completed`，可以绕过检查并覆盖 `active` 句柄。取消只能停止其中一轮；第一轮先完成时，无归属检查的 `active.delete(taskId)` 还会删掉第二轮句柄。新建接口接受重复客户端 taskId，也存在同类覆盖问题。

需在读取请求体后再次检查并独占任务执行，恢复开始时记录真实运行状态；执行结束仅释放仍属于本次执行的句柄。

### 6. 旧任务终态仍可写回新书视图

流回调有切书守卫，但[runNewTask:347](https://github.com/Recoletas/Pinax/blob/4f9bb707d2402efe28d3dc07dd9ab2b4297a2777/src/components/authoring/StoryAgentBetaPanel.vue#L347) 及后面的失败处理没有同一守卫。

A 任务运行中切 B 后，A 完成仍会把旧 taskId 写回当前面板；A 失败或取消还会向 B 的对话数组插入提示。当前第 2 项缺陷会遮住部分续跑后果，修好响应式状态后这里更易串任务。结果、错误和最终清理都应按任务启动时的作品与执行标识处理。
